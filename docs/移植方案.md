## 1. 复用什么 / 重写什么

| 层 | 判定 | 说明 |
|---|---|---|
| 转写算法与协议 | ✅ 复用 | Go/Rust 源码跨平台，交叉编译即可 |
| 进程契约 | ✅ 复用 | stdin 裸 PCM16LE 单声道 → stdout NDJSON。平台无关，**不要改** |
| 音频格式 | ✅ 契约不变 | 换的只是采集实现 |

| 悬浮窗 / 玻璃 | ⚠️ 重写 | Liquid Glass 无对应，降级为半透明条 |
| 打包签名 | ✅ 反而更简单 | Windows 无强制签名 |

> ### ⚠️ 工具链 ≠ 目标（`--target` 会失败，别用）
>
> `rustup toolchain install stable-x86_64-pc-windows-gnu` 装的是**工具链**，
> 不是给默认 msvc 工具链装 **target**。所以这样写会挂：
>
> ```bash
> cargo build --target x86_64-pc-windows-gnu ...      # ✗ error[E0463]: can't find crate for `core`
> ```
>
> 报错还很有迷惑性——它长这样，看着像 rlib 不兼容，其实只是 std 没装：
>
> ```
> error[E0463]: can't find crate for `core`
>   = note: the `x86_64-pc-windows-gnu` target may not be installed
> ```
>
> **正解：切到 gnu 工具链，不带 `--target`**（该工具链的 host 本身就是 gnu）：
>
> ```bash
> cargo +stable-x86_64-pc-windows-gnu build --release --locked \
>   --no-default-features --features streaming
> ```
>
> 另一条路是 `rustup target add x86_64-pc-windows-gnu` 给 msvc 工具链补 target
> ——能用，但等于两套工具链混着编，不如直接切干净。

> **`/usr/bin/link.exe` 是个陷阱。** 本机 `which link.exe` 会命中 MSYS2 的
> **coreutils `link`**（建硬链接的小工具），**不是 MSVC 链接器**。Rust 的
> `x86_64-pc-windows-msvc` 目标若按名字去捞链接器，捞到的就是它，
> 报错会莫名其妙。**因此 Rust 统一走 `x86_64-pc-windows-gnu`**：
> 链接器是 MSYS2 的 mingw `ld`，路径明确、不会撞名；
> 且同一套 mingw 工具链顺带把 Go 的 CGO + libopus 也喂饱了。
> 选 msvc 还得额外拉几个 GB 的 VS Build Tools，不划算。

### 路线 C —— 最小可用（先跑通通路）

**做法**：Python 单文件。按住热键录音 → 松手写 WAV → 调**现成** `codex-asr` 0.1.2 做一次性文件转写 → 粘贴。

| 项 | 值 |
|---|---|
| 工作量 | 0.5 ~ 1 人日 |
| 依赖 | Python + `sounddevice` + `pynput` + `pyperclip`；codex-asr 0.1.2 上游二进制 |
| 有 | 按键录音、粘贴、目标窗口校验 |
| 无 | 实时字幕、HUD、断线 Retry、豆包后端 |

**用途**：1 天内验证「Codex 免登录转写在这台机器上到底通不通」。通路不通，后面全白搭。

| 项 | 值 |

## 5. Windows 侧要重新踩的坑

原版 `Sources/PasteController.swift` 里全是踩坑记录，以下语义必须照搬：

| 坑 | 原版做法 | Windows 做法 |
|---|---|---|
| **修饰键未释放导致粘贴失败** | 轮询 `CGEventSource.flagsState` 等到无修饰键按住再发 | `GetAsyncKeyState(VK_LCONTROL/VK_LSHIFT/...)` 轮询 |
| **目标窗口切换** | 记录录制开始时前台 app PID，粘贴前比对 | `GetForegroundWindow()` 比对 hwnd |
| **粘贴失败不要还原剪贴板** | 刻意跳过还原，让用户能手动粘 | 同 |
| **粘贴后延迟还原剪贴板** | 50 ms 写入延迟 + 400 ms 还原延迟 | 同（慢消费者需更久） |
| **剪贴板格式全量快照** | 保留富文本/图片 | `win32clipboard` 枚举格式；纯文本场景可降级 |
| **管道背压上限** | 256 KiB 封顶后终止子进程保留录音 | 同（`subprocess` stdin 写入计数） |
| **stdout 短读** | POSIX `read` 取当前可用字节 | `subprocess.stdout.read1()` 或非阻塞 `os.read` |
| **长按阈值** | 180 ms，轻点不触发 | 同 |
| **采音开流要异步** | AVAudioEngine 起来是即时的，原版没有这个问题 | **Windows 独有**，见 5.1 |

### 5.1 采音收尾竞态：`finish()` 跑在 `start()` 前面（2026-10-02 实测）

**这是 Windows/PortAudio 独有的坑，原版 macOS 没有**——`AVAudioEngine` 启动近乎即时，而 `sd.InputStream(...)` 的**构造函数本身是同步阻塞的**：实测冷启动 227 ms，`AudioCapture.start()` 整体 122 ms。这个数字比长按阈值（180 ms）还长，于是必然出事。

**故障形态**（`tools/fn-watch.py` 实测）：

```
FN up    vk=0xFF scan=0x63 ext=1 held=0.50s
ACT stop held=0.50s bytes=0 wav=44      ← WAV 只有 44 字节头，一个采样都没有
ACT start                                ← 收尾之后才打印，顺序反了
```

**根因**：`finish()` 那一刻 `start()` 还没执行到 `self._stream = sd.InputStream(...)`，所以 `_stop_stream()` 看到 `self._stream is None`，**什么都没停**；紧接着它把 WAV 关掉、置 `None`；然后 `start()` 继续往下跑，真的把流拉起来了 —— 结果是**一个永远在采集、但没人在写的泄漏流**，而且下一次录音还会撞上它。

**判据**：不能看「WAV 多大」，要看「`finish()` 之后计数还涨不涨」。已固化成 `tools/capture-probe.py` 的 [D] 回归段：

```
finish() 那一刻 0 字节；随后 1 秒又涨了 0 字节   ← 修好后必须是 0
流是否残留：否 ✅
```

**修法**（`src/audio.py`）：

1. `start()` 把开流丢进后台线程，**立即返回**（实测阻塞 122 ms → 2.5 ms）。
2. `_settle()` 先置 `_closing = True`，再 `_opened.wait(5.0)`，最后才停流。**顺序不能反**。
3. 开流线程在 `finally` 里检查 `_closing`：已置就地关掉刚建好的流，**绝不挂到 `self._stream`**。竞态窗口由此闭合。
4. `_opened.wait` 超时 5 秒也必须往下走 —— 宁可丢一段录音，不能让热键线程永久挂住。

**遗留**：开流 ~230 ms + 长按阈值 180 ms ≈ **Fn 按下后 410 ms 才开始记音**。按住说话时人通常在按下之后才开口，一般够用。彻底消除要改成「按下即预热、过阈值再开闸」，属 M5 打磨项。

### 5.2 退出信号：非主线程里的 `sys.exit()` 不生效（2026-10-02 实测）

原版靠 `NSApplication.terminate`，Windows 侧要自己管。`main.py` 里最初写的是在 `on_complete` 末尾调 `sys.exit(0)`，**不报错、也不退出**：

| 现象 | 实测值 |
|---|---|
| `--once` 跑完一次录音，应该退出 | 进程存活 **3 分钟以上** |
| 退出码 | 拿不到（进程还在） |
| 麦克风 | 一直被占着 |

**根因**：`on_complete` 不是从主线程进来的。调用链是 `live_session._read_loop`（读引擎 stdout 的线程）→ `threading.Thread(target=...)` → `on_complete`。而 `sys.exit()` 抛的 `SystemExit` **只终结抛出它的那个线程**，主线程的循环照转不误。（顺带：这也解释了为什么不能用 `KeyboardInterrupt` 之类去兜。）

**修法**（`src/main.py`）：改成事件驱动，`_shutdown()` 可从任意线程调用、幂等：

1. `self._stop = threading.Event()`；主循环退化成 `while not self._stop.wait(0.5)`。
2. `_shutdown()` 置 `_stopping` 防重入 → `_stop.set()` → `hotkeys.stop()`。
3. **`hud.quit()` 留在 `run()` 里**，不进 `_shutdown()` —— tkinter 只能在主线程收摊。

**验证**：`=== EXIT CODE 0 ===`，一次录音后进程自行退出，麦克风立即释放。

### 5.3 麦克风被占 → 静默空录音（2026-10-02 实测，是 5.2 的连带伤）

**故障形态**：假引擎如实回显 `收到 0 字节音频，约 0.00 秒`。看着像后端坏了，实际是**麦克风一帧都没出**。

**现场**：5.2 那个没退出的僵尸进程（PID 11352，19:30 启动）握了麦克风 15 分钟（19:30–19:45）。此后新起的实例**流能正常打开、不报任何错，但收不到一帧数据**——PortAudio 的共享模式流被饿死。链路每一段都是绿的，结果为空。

**为什么难查**：空音频被照常灌进引擎，引擎照常回一句关于 0 字节的话，用户看到的是**引擎的回显**，于是去查后端。真正的信号（麦克风没出声）在链路上游，而它不报错。

**修法**：

| 位置 | 改动 |
|---|---|
| `src/audio.py` | 新增 `_pcm_bytes` 计数（`_callback` 里与落盘同一把锁内累加），对外暴露 `bytes_captured` / `seconds_captured` |
| `src/main.py` | `on_stop()` 里 `capture.finish()` 之后**先体检再 `session.finish()`**：不足 `MIN_CAPTURE_SECONDS = 0.10` 秒就 `_abort_capture()` —— 撤掉会话（引擎都不启动）、删掉空 WAV、提示原因，**不送后端** |

**0.10 秒这个阈值怎么来的**：热键要求按住 ≥180 ms 才起录，开流又吃掉约 176 ms，所以最短的**有意图**的按住（约 0.3 秒）也能采到 ~0.12 秒，卡 0.10 不误伤；真正坏掉的情况实测就是 0.00 秒。提示文案按两种情形分开：

| 采到 | 文案 | 指向 |
|---|---|---|
| 0 秒 | 麦克风没出声（0 秒） | 设备被别的程序占着（含上一次没退干净的 Voice Pill），或刚被拔插 |
| 0 < t < 0.10 秒 | 录音太短（t 秒） | 按住主键的时间再长一点 |

**固化**：`tools/capture-probe.py` 的 [D]/[E] 段现在同时校验闸门输入（`seconds_captured=0.00 秒 → 跳过后端 ✅`）与计数器自洽（内部计数必须与 `on_pcm` 收到的字节数逐字节相等）。

**操作建议**：上一条僵尸就是「同时起了两个 `main.py`」的后果之一。调试期一律用 `timeout 150 python src/main.py --once` 包一层，别让"跑完不退出"留下占着麦克风的进程。

## 6. 键位设计（必须解决的硬问题）

**Windows 上 Fn 由键盘固件/EC 处理，绝大多数笔记本不上报给 OS**，`WH_KEYBOARD_LL` 收不到。方案：

| 候选键 | 优点 | 缺点 |
|---|---|---|
| **右 Ctrl** | 几乎无人用右 Ctrl，位置顺手 | 部分键盘无右 Ctrl |
| **右 Alt** | 同上 | 某些布局是 AltGr，会打字符 |
| **Caps Lock** | 位置极顺手 | 会牺牲大小写锁定；需改注册表关掉原功能 |
| **鼠标侧键** | 完全不占用键盘 | 需额外监听鼠标 |
| **长按 F1~F12 之一** | 通用 | 与其他软件冲突 |

**建议**：默认 **右 Ctrl**，并做成可配置项，首次启动引导选键。

> ⚠️ **以上是「实测前」的备选清单，已被 6.1 的实测结果取代。**
> 本机（ThinkPad T14p Gen 2）的 Fn **确实会上报给 OS**，所以主键直接用 Fn，
> 这份清单降级为「换机器/换键盘时的回退候选」。
> 落点在 `src/config.py: PRIMARY_KEY_CHOICES`（`fn` 为默认，其余四个仍保留）。

### 6.1 本机硬件（2026-10-02 实测）

| 项 | 值 |
|---|---|
| 机型 | Lenovo **ThinkPad T14p Gen 2**（`21KUA004CD`，`LENOVO_MT_21KU_BU_Think_FM_ThinkPad T14p Gen 2`） |
| 键盘设备 | `ACPI\LEN0071`（PS/2 标准键盘）+ `HID\INTC816&COL01`（HID 键盘） |

ThinkPad 的 Fn 由 **EC（嵌入式控制器）**处理。利好：BIOS 有 `Fn and Ctrl Key swap`、`F1–F12 as primary function` 等固件级选项，Lenovo Vantage 也能改 Fn 行为。风险：多数 ThinkPad 单独按 Fn **不向 OS 上报键码**。

**因此先跑探针实测，不预设结论。** 探针：`tools/fn-probe.py`（Raw Input + 低级钩子双通道）。

#### 探针实测结果（2026-10-02，两轮）

**结论：本机 Fn 会上报给 OS，且按下/松开成对 → 主键定为 Fn，可用「按住说话」。**

| 项 | 实测值 |
|---|---|
| 扫描码 | `0x63`，带 `E0` 扩展前缀 |
| vkCode | `0xFF`（无虚拟键映射——**必须认扫描码，不能认 vk**） |
| 可达通道 | HOOK 与 RAW **两条都抓得到** |
| 按下事件 | `WM_KEYDOWN` (`msg=0x0100`)，两轮共 23 次 |
| **松开事件** | **有**。`WM_KEYUP` (`msg=0x0101`)，两轮成对 |
| Fn + Esc | **零事件**。Fn Lock 在 EC 里完成，Windows 完全看不到（Esc 的 `0x01` 全程没出现） |
| 实测按压时长 | 0.11 / 0.44 / 0.45 / 0.45 / 0.46 / 0.53 / 0.58 / 0.73 / 2.15 s |

原始日志：`fn-probe.log`（第一轮，全键）、`fn-probe2.log`（第二轮，`--keyup --only 0x63`）。

两点提醒：

1. **第一轮探针自带判读误报。** 它只把 `scancode=0x00 vkCode=0x14`（Caps Lock 在 RAW 通道的怪癖）列为「非标准项」，反而漏掉真正重要的 `E0 63`。那个过滤条件写偏了 —— 看日志要**自己读去重表**，别信它的自动结论。
2. **第二轮结尾的「对照组 A/B 未抓到」也是误报**，因为该轮加了 `--only 0x63` 过滤，A/B 本就被滤掉。判读逻辑不认识 `--only` 这个开关。

> 探针为此加了两个开关：`--keyup`（记录松开事件）和 `--only 0x63`（只过滤指定扫描码）。默认行为不变。

**副作用：`pynput` 依赖被移除。** `vkCode=0xFF` 是无映射键，pynput 会不会原样透出未知；而裸 `WH_KEYBOARD_LL` 已被实测证明可用。`src/hotkey.py` 因此改为自己用 ctypes 挂钩子，顺带去掉一个依赖。

### 6.3 收不到键盘输入——已定论：不是进程的问题（2026-10-02）

**现象**：用 `tools/shell-selftest.py`（热键 + 采音，不依赖 ASR 引擎）验证热键链路，**从自动化工具拉起的 Python 进程，45 秒和 60 秒各跑一轮，原始按键事件都是 0 条**（连普通字母键都没有），而 `SetWindowsHookExW` 并没有报错——典型的「静默成功」。

早先还有一组更迷惑的数据：同一个 `fn-probe.py`，人手动跑抓到 23 次 Fn 按下，自动化跑是 0 条。

**当时的两个假设**：(1) 那段时间没人在按键；(2) 自动化拉起的进程不在交互桌面上，低级钩子绑桌面，跨桌面收不到。

**现在逐条证伪/证实：**

| 判定项 | 工具 | 实测结果 | 说明 |
|---|---|---|---|
| 窗口站 / 桌面 | `tools/desktop-probe.py` | `WinSta0` / `Default` | ✅ 就在交互桌面上 |
| 会话号 / 完整性 | 同上 | 会话 1，`0x2000 Medium` | ✅ 没有被沙箱降权 |
| 钩子 + 消息泵 | 同上（`SendInput` 自激自收） | 发 2 条收 2 条 | ✅ 链路本身是通的 |
| 会话里有没有物理输入 | `tools/input-liveness.py` | 60 秒内 `GetLastInputInfo` 跳了 187 次 | ✅ 输入在流动 |
| 钩子能不能看到物理输入 | 同上（同一次运行） | 第 176 次起钩子开始计数，最终 **21 条** | ✅ **能看到** |

**结论：假设 (2) 不成立。** 进程在交互桌面上、钩子链路完好、物理输入也能看到。那几次 0 条的唯一解释是**假设 (1)——窗口期内确实没人按键盘**。

注意 `input-liveness.py` 那一轮的形态很说明问题：**前 175 次输入事件钩子全是 0 条**——因为那是**鼠标**（`GetLastInputInfo` 键鼠都算，`WH_KEYBOARD_LL` 只算键盘）。直到人开始打字，第 176 次起钩子才开始计数。所以「会话有输入」和「键盘被按了」是两件事，不能混。

**为什么早先误判成"后台不行"**：跑完 60 秒、心跳显示进程活满全程、输出 0 条，就把 0 条归因给了进程。实际上没人按键和进程看不见输入，输出长得一模一样。**这是判据缺失，不是环境限制。**

**修正后的规矩：**

1. 涉及 `WH_KEYBOARD_LL` 的验证**可以**由自动化跑，不必非得人手动。
2. 但**任何时候都不许把「0 条」当成结论**——必须先证明窗口期内真有按键。`tools/input-liveness.py` 就是干这个的（鼠标动一下即可，不用按键）。
3. 测 Fn 这种「要人等」的项，别用固定窗口。用 `tools/fn-watch.py`：只打命中主键的行，默认听 900 秒，随时按都算数。理由是实测中 60 秒窗口里人往往在往输入框打字，134 行字母键把真正要看的 Fn 淹没了。

**本次顺手踩到的两个 ctypes 坑（都写在 `desktop-probe.py` 注释里）：**

| 坑 | 症状 | 真因 |
|---|---|---|
| `INPUT` 结构体只留了 24 字节联合体 | `SendInput` 返回 0，`err=87 ERROR_INVALID_PARAMETER` | x64 上 `MOUSEINPUT` 是 32 字节，系统眼里 `sizeof(INPUT)` = 40，`cbSize` 不等就一条都不发 |
| `GetCurrentProcess()` 没声明 `restype` | `OpenProcessToken` 报 `err=6 ERROR_INVALID_HANDLE` | 伪句柄是 64 位 `0xFFFFFFFFFFFFFFFF`，默认按 `c_int` 收成 `0xFFFFFFFF`，不再是合法伪句柄 |

两个都是**函数成功返回但结果无效**的类型，不看错误码根本发现不了。

### 6.4 凭据通路实测：三个后端全断（2026-10-02）

第 9 节把「Codex 免登录通路不通」列为**高风险**，实测下来风险应验，而且是**三路都不通**。

用 SAPI 合成一段真语音（`tools/make-test-audio.ps1`，发音人 Microsoft Huihui Desktop zh-CN，8.93 秒），转成裸 PCM（`tools/wav-to-pcm.py`）分别灌给两个引擎，**绕开麦克风和热键**单独验引擎通路。

| 后端 | 实测命令 | 结果 |
|---|---|---|
| Codex | `codex-asr.exe stream --sample-rate 24000 --input tmp/test-24k.pcm` | ❌ `Codex auth at ~\.codex\auth.json does not contain a ChatGPT access token` |
| 豆包 | `cat tmp/test-16k.pcm \| freeasr.exe live --quiet` | ❌ `rpc error: code = 2 desc = service discovery failure` |
| 本地中转 | `curl 127.0.0.1:15721/v1/models` | ❌ `HTTP 000`，端口没监听 |

**Codex 的真因**：`~\.codex\auth.json` **只有 39 字节**，内容是一个 13 字符的 `OPENAI_API_KEY` 占位符，**没有 `tokens`**（OAuth 令牌）。而且 `~\.codex\config.toml` 指向 `base_url = "http://127.0.0.1:15721/v1"` 的**本地中转**（`requires_openai_auth = true`、模型 `deepseek-flash`），说明这台机器的 Codex CLI 压根没走官方 ChatGPT 后端。

> ⚠️ 教训：自检里「文件存在 = ✅」是**假阳性**。`main.py --check` 原来就只看 `auth.json` 在不在，报 ✅ 而引擎照样失败。已改成**读内容**判 `tokens.access_token`，现在会明确报「只有 OPENAI_API_KEY（13 字符），无 ChatGPT OAuth 令牌」。
> **解**：跑 `codex login` 用有转写权限的 ChatGPT 账号重新登录。

**豆包的真因**：不是网络、不是代理（系统代理 `ProxyEnable=0`，已关；环境变量也无）。verbose 日志显示链路是**通的**：

```
loaded credentials from file  device_id=3119778226010346
connecting to ASR  url=wss://frontier-audio-ime-ws.doubao.com/ocean/api/v1/ws
ASR session ready  request_id=36766590-f91d-4f10-876d-c615eed47de0
→ Error: ASR: read backend response: rpc error: code = 2 desc = service discovery failure
```

WebSocket 握手成功、会话就绪，**服务端**才回错。文件转写（`transcribe`）与实时（`live`）两条路报同一个错，重试一致。且 —— 关键佐证 —— `service discovery failure` 这个串**不在客户端源码里**（`grep` 过整个 `vendor/FreeASR`），是服务端原样透传的。

客户端伪造的是豆包输入法安卓端（`internal/protocol/constants.go`：`aid=401734`、`version_name=1.1.2`、Pixel 7 Pro 的 UA）。字节跳动侧不再给这条逆向协议路由 —— **本机无解**，只能等上游适配。

> ⚠️ 附带发现：`freeasr doctor`（本该只读的体检命令）**会自动注册设备并申请令牌**，凭据写到 `~\.config\freeasr\credentials.json`。属该工具自身设计，但首次跑会静默产生一次对外注册。

**当时可用的替代**：`tools/mock-asr.py` —— 实现 NDJSON 契约但不真转写，把「收到多少字节音频」当转写文本回吐。用它可把链路里**除转写之外**的每一段（钩子、采音、重采样、管道背压、解码、粘贴）先钉死；粘出来的字节数与录音时长对不上就说明管道丢包。挂法：

```bash

#    bash 下裸着的 & 是「后台运行」运算符，命令会在此断句；
#    cmd  下裸着的 & 是命令分隔符，`set` 会在此截断，赋进去的值只剩前半截。
VOICEPILL_ENGINE="D:\Own_tools&skills\voice-pill-windows\tools\mock-asr.py" .venv/Scripts/python.exe src/main.py

### 6.5 后端选型定案：本地离线 SenseVoice（2026-10-03）

**复验过程**

| 假设 | 怎么验的 | 结论 |

  代理关掉后 GitHub Releases 与 hf-mirror 都超时，PyPI 与 ModelScope 正常 ——
  所以模型别从 GitHub 拿。

| 项 | 值 |
|---|---|
| 识别速度 | RTF **0.027**（8.93 秒音频 0.245 秒出结果） |
| 准确度 | SAPI 合成句一字不差：`这是一段测试语音，用来验证语音转写引擎是否工作正常。今天天气不错。` |

| 中间结果 | 截前 3 秒能出「这是一段测试语音，用来验证。」；管道自测全程 8 条递增快照 |

**代价**：模型体积与首次下载；换机或换模型要重新指定 `local_model_dir`。
**收益**：不联网、不要账号、没有额度与封禁风险，也不受任何服务端改动影响。

> `codex` 与 `doubao` 两个后端**保留在代码里**，没有删。凭据已生成、provider
> 已写好，哪天 ChatGPT 订阅到位或豆包协议恢复，改 `settings.json` 一行就能切回。

## 11. 常驻形态（2026-10-03，M5 提前）

M1–M2.5 打通的是「**能**用」。真按 Fn 说话验证通过之后，用户的要求变成
「这个能力我肯定需要**常态化驻留**」。这两件事之间差的不是功能，是一整套外壳：
原来那套是「手动跑一次」的写法——前台黑窗口，关掉窗口就等于杀掉进程；
两个实例会各采一遍麦克风、各粘一遍；钩子哑了没有任何提示；录音和日志只增不减。

### 11.1 做了什么

| 问题（原写法会怎么坏） | 做法 | 落在哪 |
|---|---|---|
| 两个实例会各粘一遍 | 命名互斥体（内核持有，进程无论怎么死都自动释放，不留锁文件） | `src/single_instance.py` |
| 没有窗口 = 崩了查不到 | **总是**写 `logs/app.log`，有控制台再镜像一份；2 MB 滚动 | `console.attach_app_log()` |
| 关掉窗口就没了 | 启动文件夹快捷方式挂 `pythonw`（GUI 子系统，不弹黑窗口） | `src/autostart.py` |
| 崩了就一直不在 | 看门狗重拉；子进程 code 0 则一起退；短时连崩 3 次放弃 | `src/supervise.py` |
| keyup 丢了会一直录 | 时长护栏（默认 120 秒），到点**截断并照常转写**，不丢已说出的内容 | `main.RecordWatchdog` |
| 钩子哑了没人知道 | 每 30 秒体检，线程没了就整条重装（钩子 + worker + 队列） | `hotkey.alive` / `restart()` |
| 录音/日志只增不减 | 成功即删本次日志；失败留存按分钟清（默认 3 分钟，扫描周期 1 分钟）；只碰 `rec-*` | `config.prune_data()` |
| 换个后端要重启 | 每 2 秒看 `settings.json` 的 mtime，能热改的就地生效（悬浮条开关如实标注"需重启"） | `main._check_settings` |
| 停不掉后台进程 | `--stop` 置命名事件，走完整收摊（拔钩子、关悬浮条、写日志尾） | `single_instance.request_quit()` |
| 悬浮条一出现就抢走前台 | 钉成 `WS_EX_NOACTIVATE`（出现/被点都不激活）+ `WS_EX_TRANSPARENT`（鼠标穿透），每次 `show` 都重设一遍 | `hud._harden()` |

### 11.2 为什么自启挂的是看门狗，不是真身

计划任务自带「失败后重启」，本来是最优解。**但本机非管理员注册不了任何计划任务**：
`Register-ScheduledTask`（三种 principal 写法）与 `schtasks /create /sc onlogon`
全部 `Access is denied`（2026-10-03 实测）。于是落到启动文件夹快捷方式，
而它**没有**重启策略——缺口用看门狗补上。

两条路装出来是同一个东西（`pythonw src/supervise.py`），这一点比"哪条路更好"更重要：
否则「我明明装了自启，怎么不拉」会因为走哪条路而不同，这种不确定最难查。
哪天有了管理员，重跑一次 `--install-autostart` 就会换成计划任务，多一层系统级重启。

> **2026-10-04 变更**：默认形态改成「随 Codex 起落」（见第 17 节），**开机自启不再默认安装**——
> 登录时不会有看门狗空跑；代价是不开 Codex 时按 Fn 不会有反应。
> `--install-autostart` 保留给「不开 Codex 也想按 Fn 用」的机器，两条路装出来仍是同一个东西。

看门狗的策略每条都有理由：
* 子进程 **code 0 → 一起退**。0 只可能来自 `--stop` / Ctrl+C，绝不能
  "你以为停了其实又起来了"。
* 非 0 → 隔 5 秒重拉。
* 60 秒内崩够 3 次 → 放弃并写日志。否则一个坏配置（模型目录被移走之类）会变成
  每 5 秒一次的无限重启，机器被反复折腾，用户在任务管理器里还会看到它一遍遍冒出来，
  比直接不工作更吓人。

### 11.4 被自测抓出来的一个真问题

第一版日志是「**仅当 stdout 为 None 时**才记账」。自测立刻红了：`pythonw` 被

这比没有黑匣子更糟。改成无条件记账 + 有控制台就镜像到屏幕，全绿。

## 12. 控制面：让外部进程驱动它（2026-10-03）

### 12.1 为什么需要

常驻形态原本对外只有两个口子：`--stop` 的一个命名事件，和 `settings.json` 热重载。
都不够用——Codex 插件那侧要能问状态、要能让它录一次、要能把它刚转出来的文字取走。

### 12.2 选了命名管道

* 管道不带网络栈：不会触发防火墙弹窗，也不存在被别的机器连上的可能。
* 标准库 `multiprocessing.connection` 在 Windows 上就是命名管道，authkey 握手
  也一并给了，不必手写 Win32 那一套。
* 密钥落 `%LOCALAPPDATA%\VoicePill\bridge.key`（用户 ACL 天然隔离），两端谁先起
  谁造，后起的读。

命令只有七个：`status` / `start` / `stop` / `cancel` / `take` / `speak` / `shutup`；
一次连接一条请求，请求与响应各一行 JSON。命令集合刻意留小：这条通道每多一个
动词，就多一份「同机进程能拿它干什么」的想象力。

`speak` / `shutup` 是第 16 节发声能力进来的（`speak` 的 `auto=True` 是给回合结束
钩子用的：`speak_replies=false` 时直接跳过）。加这两个动词**不扩大能碰到的东西**
——它们只能让本机扬声器出声或闭嘴，读不到任何数据、也不落盘。这也是把 TTS 做成
常驻实例的一个能力、而不是另开一个服务的理由：单实例、看门狗、日志、护栏全都白拿。

### 12.3 `take` 是取走语义 + 保鲜期

返回并清空（内存里保留最近 20 条，进程一退就没，**不落盘**）。改口供的场合比反复读
同一段多得多，清空之后队列里也不会一直堆着用户说过的话。

队列是被动的：它只在用户下一次往 Codex 发消息时才被取走。所以每条转写带一个时间戳，
`take` 只返回保鲜期（`settings.pending_ttl_minutes`，默认 30 分钟，0 = 不过期）内的，
过期的直接丢弃。没有这道时效的话，几天前随口说的一句会在几天后被一起塞进一轮对话，
和当时真正的意图搅在一起。

### 12.4 验证到哪一步

* 协议隔离自测（单进程起服务端）：status / take / start 往返正常；处理器抛异常
  原样回报给对端；`stop()` 之后连不上、`probe()` 返回 None。
* 真实驻留进程：`main.py --check` 的「控制面」一行显示 `✅ 在听（pid … idle）`。
* 端到端：用户按 Fn 说的两句被队列收下，经 `take` 原样取回。
* 保鲜期由真实方法单测覆盖：30 / 0 / 5 / 负数分钟各边界、20 条上限、二次 `take` 幂等。
* 协议**与坏输入**：`tools/bridge-selftest.py`（20 项全过）—— 坏输入那一半是
  12.5 那个 bug 之后补的尺子。

### 12.5 事后揪出来的一个真 bug：全局管道名 + 没有上限的握手

这一节记在控制面下面而不是第 16 节：**问题是第 16 节的发声自测踩出来的，
但坏的是控制面本身。**

原来的写法有两处单独看都不算错、凑一起就致命：

* **管道名是全机共用的**：`\\.\pipe\VoicePill`，所有用户一个名。
* **客户端的 authkey 握手没有超时**：`Client()` 那一步没有超时参数。

于是"管道名对、密钥不对"——另一个用户的 `%LOCALAPPDATA%`，或者密钥文件被
删掉重建之后——这一个组合同时踩坏两边：

| 一侧 | 后果 |
|---|---|
| 服务端 | `accept()` 抛 `AuthenticationError`。它**不是 `OSError`**，`_serve` 里那条 `except OSError` 接不住，异常直接把 accept 线程带走——**控制面永久失联，而驻留进程自己毫不知情**：进程还活着、按 Fn 录音粘贴照常，只有插件那一侧永远连不上 |
| 客户端 | 服务端已经走人，客户端还卡在 `recv` 上等回应，**永不返回**（实测 12 秒以上仍不回来） |

代价是实测的：拉这份代码之前跑着的那个驻留实例（pid 26904），控制面就是这么死的。

三处一起改才够：

1. **管道名带用户标识**：`\\.\pipe\VoicePill-<sha256(normcase(app_dir()))[:16]>`。
   标识从 `%LOCALAPPDATA%` 推出来，不调 Win32——控制面两端读的是同一份环境变量，
   算出来必然一致。好处是"密钥不对"的客户端**连管道都找不到**，直接 `OSError`
   快速失败，两边都安全。另留 `VOICEPILL_PIPE_NAME` 整个覆盖，给自测用。
2. **客户端建连有上限**：`_connect()` 把 `Client()` 放进旁路线程，`join(3.0)`，
   到点报 `BridgeError`。握手没有超时参数，只能这么卡。代价写在那个函数的
   docstring 里：超时之后线程还挂在 `recv` 上（Python 杀不掉阻塞在系统调用里的
   线程），靠 daemon 线程随进程退出兜底——调用方全是短命进程，够用。
3. **服务端不被坏连接带走**：`_serve` 除 `OSError` 外再单独接一条 `except
   Exception`，记进 `last_error` 然后 `continue`。Listener 还活着，下一个正常
   客户端照样能连。

尺子：`tools/bridge-selftest.py`（20 项全过），**专盯坏输入**——

* 管道名按用户派生、同一用户两次算出来一致、环境变量能覆盖
* 协议往返、未知命令在客户端就被拦、处理器抛异常时对端拿得到人话且不等超时
* **错密钥的客户端必须有上限地返回**；**控制面必须还活着**；**错密钥之后正常
  客户端照样能用**（最后这条是核心——改之前的写法过不去）
* `stop()` 之后 accept 线程收工、调用报错而不是静默

连带修的还有 `tools/speak-selftest.py` 里那段 Stop 钩子测试：它原来会被这条
历史路径牵连（既打死真身、又慢到超时）。现在两个环境变量一起给（临时
`LOCALAPPDATA` + 测试专用管道名），彻底在体外跑。

## 13. Codex 插件（2026-10-03）

### 13.1 插件只做控制面客户端

采音、转写、粘贴、常驻、开机自启全在第 11、12 节那一个进程里；插件不重造这些。
理由和 12.1 同源：引擎那侧要装模型、引擎二进制、低级键盘钩子，还要在 Codex 没开着的
时候也能用，塞进插件进程只会得到两份实现和两份状态。

插件给 Codex 的是八个工具（status / listen / stop / cancel / take / speak / shutup /
prompt_hook）加两个钩子：`UserPromptSubmit`（把待取文字注入当轮）和 `Stop`
（回合结束后按需把回复念出来，见第 16 节）。`UserPromptSubmit` 是这套东西真正的
用法：**按 Fn 说的字，接着你在 Codex 里敲的那一句话一起进来**，不用你先去调一次工具。

### 13.2 两条硬约束（都实测过，别绕）

**一、命令路径不能含 `&`。** 本仓库在 `D:\Own_tools&skills\...`，三种写法实测：

| 写法 | 结果 |
|---|---|
| `D:\Own_tools&skills\...\hook.cmd`（不加引号） | `hook: UserPromptSubmit Failed`——cmd 在 `&` 处把命令拆断了 |
| `"D:\Own_tools&skills\...\hook.cmd"`（加引号） | Codex 回 `Completed`，但脚本**根本没跑**（plugin.log 无记录）——假成功，比失败更坑 |
| `C:\Users\<用户>\plugins\voice-pill\hook.cmd`（不含 `&`） | `Completed` 且 plugin.log 有记录 |

所以插件在 Codex 眼里固定住在 `%USERPROFILE%\plugins\voice-pill`，由**目录联接
（junction）**指到本仓库的 `plugins/voice-pill`：仓库是唯一源码，Codex 看到的路径不含 `&`，
个人市场清单沿用官方默认写法（`./plugins/<名字>`）不用改一个字。

顺带一条判据：**`Completed` 不等于跑过了**。只有 plugin.log 里出现对应的
`hook_prompt_submit session=…` 才算数。

**二、插件内的路径只能是绝对路径。** Codex 会把插件整包拷进自己的 cache，相对路径在
那边解析不了（实测 `.mcp.json` 写相对 command 直接报 `os error 3`）。涉及
`.mcp.json` 的 command/args 和 `hooks/hooks.json` 的 command 三处，由
`plugins/install.py` 按当前机器生成。

### 13.3 校验器和运行时对不齐

官方校验脚本的白名单是手写的：它**拒** `plugin.json` 里的 `hooks` 字段
（`field 'hooks' is not accepted by plugin validation`），而运行时认这个字段。
独立文件 `hooks/hooks.json` 是唯一同时过两边的写法（校验器 PASS，运行时也确实加载）。

### 13.4 验证到哪一步

* 钩子被运行时加载并真的执行：`codex exec` 输出 `hook: UserPromptSubmit Completed`，
  且 plugin.log 有同 session 的 `hook_prompt_submit` 记录。
* 注入确实进了模型输入：会话 rollout jsonl 里以 `role: developer` +
  `content_item_kinds: ["hooks.additional_context"]` 出现。
* 钩子三分支：队列有字 → `hookSpecificOutput.additionalContext` 带原文；队列空 →
  `{"continue": true}`；只有空白 → 同上（桩测，不起进程）。
* MCP：服务端起来（plugin.log `server_start`），八个工具注册正常。
* `Stop` 钩子四种载荷（有正文 / 空载荷 / 空正文 / 不是 JSON）都是 rc=0 + 一行
  `{"continue": true}` + 5 秒内返回：它绝不能因为 TTS 出问题而拖慢或拦住一个回合。
* `plugins/install.py` 的 `--check` 与实跑各一次，可反复跑不脏工作区。`--check` 会
  **问 Codex 自己**（`codex plugin list`）确认插件装没装，问不到就报「无法确认」
  而不是放行——2026-10-04 补：那天的升级把插件从应用侧丢了，而当时的 `--check`
  会盲报「就绪」。尺子 `tools/install-selftest.py`（20 项）。

## 14. 交付护栏：堵掉「按 Fn 没反应」这条路（2026-10-03，对照上游 0.2.4）

### 14.1 上游修了什么

上游 0.2.4（`cdf917b`）的提交标题就是 `Fix Fn lockout after interrupted paste`。
作者在 `docs/VERIFY-0.2.4.md` 里把现场记了下来：

> The running 0.2.3 app was busy with no transcription child, and ignored Fn.

翻译成状态机的语言：**粘贴路径上有一个提前 return，把状态留在了 `inserting`
（忙）**，而 Fn 的准入条件恰恰是「空闲才受理」，于是热键被自己永久挡在门外——
没有崩溃、没有报错、没有日志，只有「它有时候不灵」，重启才好。

0.2.4 的修法三条：① 提前返回也必须解锁；② 8 秒停滞看门狗，作废这次尝试；
③ 代际令牌，迟到的旧回调改不了新会话。

### 14.2 我们这版的对等缺口（同一个病）

Windows 版没有 `inserting` 这个阶段，但闸门一模一样：`on_start` 只受理
`Phase.IDLE`。而交付路径上：

| 位置 | 原来会怎么坏 |
|---|---|
| `on_complete` 的粘贴 | **只捕 `PasteError`**。换成 `OSError`（剪贴板被别的程序占着）之类就一路抛穿，后面的 `_reset()` 轮不到执行，`phase` 永远停在 `TRANSCRIBING` |
| `on_stop` 的收尾 | `capture.finish()` / `session.finish()` 抛异常同样让 `TRANSCRIBING` 卡死 |
| 停滞兜底 | **没有**。`RecordWatchdog` 只在 `RECORDING` 期间武装（`arm()` 在 `on_start` 末尾、`_reset()` 里解除），转写/粘贴阶段裸奔 |
| 回调线程 | `live_session._finish_once` 把回调丢进一个 daemon 线程，异常只在那条线程里炸掉，**没有任何人看得到** |

结果是同一个症状：按 Fn 静默失效。

### 14.3 做法

新增 `src/delivery.py`（`DeliverySession`，上游 `DeliverySession.swift` 的等价物）
＋ `main.py` 里三处接线：

| 改了什么 | 落在哪 | 为什么 |
|---|---|---|
| 交付包在 `with self._delivery.run() as gen:` 里 | `main.on_complete` | 出块必解除看门狗；无论怎么返回都不会把状态留脏 |
| 停滞到点 → 强制回 IDLE | `main._on_delivery_stalled` | 看门狗线程上只做「解锁」，**不去碰那次仍在阻塞的粘贴** |
| 兜底捕获 + `_reset()` | `main._delivery_crashed` | 把「静默锁死」变成「一次可恢复的失败」；原始异常进日志 |
| 粘贴捕获放宽到 `Exception` | `main._deliver` | 上游 0.2.3 正是让它穿透出去的。文字既然已在剪贴板，就按粘贴失败处理 |
| 代际自查 | `main._deliver` 末尾 | **看门狗自己引入的新风险**：解锁后用户可能已经在录下一句了，此时旧交付去删 WAV、复位状态、覆盖字幕，就是砸新会话 |
| 状态迁移日志 | `main._set_phase` | 这类故障全都「没有可见症状」。日志只记状态与代际，**不记说话内容** |

第 5 条值得单独说：它不是照搬，是**必须配套**。看门狗把「卡住」变成「解锁」，
解锁之后系统里就同时存在两个活着的交付代际了——没有令牌，护栏反而会制造新 bug。

### 14.4 验证到哪一步

两个尺子，都不需要人、不需要麦克风、不需要网络：

| 工具 | 量什么 | 结果 |
|---|---|---|
| `tools/delivery-selftest.py` | 护栏原语：提前返回解锁、成功不误报、停滞只作废一次、迟到看门狗无操作、锁序无死锁 | 11 项全过 |
| `tools/delivery-fault-selftest.py` | **真状态机故障注入**：粘贴卡死 → 自动解锁；随后开的新会话不被旧交付删 WAV／复位／覆盖字幕；非 `PasteError` 异常也解锁；正常交付不改味 | 16 项全过 |

其中「锁序」那条是移植版特有的回归：看门狗跑在自己的线程上、回调方持有自己的
锁，顺序写反就是死锁，而且只在超时那一刻才现形。自测里带 20 秒硬超时，宁可报
失败也不挂住。

`main.py --check` 仍为「✅ 就绪」。

### 14.5 边界（说清没做什么）

* 停滞上限 **8 秒，与上游同值**；自测里直接断言这个数，防止哪天被拍脑袋改掉。
* **没有新增门禁**。这次改的全是「把卡住变成可恢复」，不是给用户加限制。
* **没有加 `INSERTING` 阶段**（上游 0.2.4 加了）。`Phase` 经控制面 `status`
  外泄给插件，加值要先单独议契约——不与本修复混在一起做。
* 常驻进程要**重启**才吃到这个修复（改的是启动时加载的代码）。

## 16. 发声：让它回话也能听见（2026-10-03）

### 16.1 为什么是离线神经 TTS，不是云 TTS

到第 15 节为止，全链路是**单向**的：你说 → 出字。要成"对话"就得补上反方向。
选型沿用 6.5 定的那条线：**运行时不依赖网络与凭据**。

云 TTS 更省事、音色更多，但它会让整个工具在断网/换机时变成半成品。ASR 已经因为
这条线从云端退回本地了，TTS 没有理由再往外走。引擎沿用已经在用的 sherpa-onnx
（`OfflineTts`），不引入第二个运行时、也不新增一份要维护的凭据。

### 16.2 模型放哪：代码里不写盘符

模型落 `D:\VoicePill-models\kokoro-multi-lang-v1_1\`（解压后约 407 MB），
**和 ASR 模型并排**。取目录的规则在 `config.tts_model_dir()`，优先级：

1. `settings.json` 的 `tts_model_dir`（显式指定，最高优先）
2. 环境变量 `VOICEPILL_TTS_MODEL`
3. **兜底：`dirname(local_model_dir()) + "kokoro-multi-lang-v1_1"`** —— 不写任何盘符。
   ASR 模型挪到哪，TTS 模型就跟到哪

第 3 条是有意的：代码里写死 `D:\` 的配置，换机/换盘时必然变成一条假报错。
自测里有一条专门查这个——`dirname(TTS 目录) == dirname(ASR 目录)`。

### 16.3 音色：103 个 sid 的真实名字与分组

`settings.tts_speaker` 是 sid（整数）。名字与 sid 的对应关系来自上游仓库
`hexgrad/Kokoro-82M-v1.1-zh` 的 `voices/` 目录**顺序**：

| sid | 音色名 | 说明 |
|---|---|---|
| 0–2 | `af_maple` / `af_sol` / `bf_vale` | 英语音色 |
| 3–57 | `zf_001` … `zf_099`（55 个） | 中文女声 |
| 58–102 | `zm_009` … `zm_100`（45 个） | 中文男声 |

**`voices.bin` 只存向量、不存名字**，所以这张表是"顺序 + 数目"推出来的。推断不能
只靠推断，两条独立证据把它验成了事实：

* **基频实测**（`tools/tts-voice-map.py --probe`）：103 个 sid 各合成一句后估基频，
  女声区 156–350 Hz（中位 261）、男声区 109–222 Hz（中位 147），**分界线正好落在
  57/58**，与"55 个 `zf_` + 45 个 `zm_`"的数目完全吻合。合成带随机性，重复跑会有
  几 Hz 抖动，所以自测算的是"分界线成立"而不是某个具体数值。
* **受控对照**：取上游自带的 `samples/HEARME_zf_001.wav` 的第一句
  （`Kokoro 是一系列体积虽小但功能强大的 TTS 模型。`），与本地 `sid=3` 用**同一句、
  同一语速**合成比对——F0 中位 **260.9 Hz vs 266.7 Hz**，10–90% 区间 `211~324` vs
  `207~312`，F0 分布几乎重合，是同一个说话人。而邻居 `sid=6` 是 226 Hz、
  `sid=59` 是 134 Hz，都明显不是。

完整映射 `sid → 音色名` 由 `tools/tts-voice-map.py` 直接打印，**不手抄进文档**
（手抄过的口径必然漂移）。换模型或换错包时，`--probe` 会立刻报警。

### 16.4 三个实测参数（都有依据，不是拍脑袋）

| 参数 | 值 | 依据 |
|---|---|---|
| `tts_threads` | **8** | 实测 RTF：2 线程 0.63 · 8 线程 **0.43** · 18 线程 0.77。核多反而慢，所以写成可配项，而不是 `cpu_count()` |
| 加载 | 1.7–2.2 s | 325 MB 的 `model.onnx`。所以**懒加载**：常驻进程开机不该为一个可能用不上的能力背内存，第一次真要说话时才加载 |
| 播法 | **整段一条输出流 + 合成预取一句** | 第一版是「合成一句、播一句、每句重开流」，实测**每句白送 0.34 s 设备开关 + 下一句的合成时间（2.0 s）**，一段两句的回话中间能空出 2 秒多。改成整段只开一条流、合成线程预取下一句之后，边界上只剩模型自己的句末停顿。见 16.8 |

### 16.5 打断是硬要求

`stop()` = 置中断事件 + `stream.abort()` + 清空待播队列。**按 Fn 之后的第一件事
就是调它**（`on_start` 开头）。这是"对话"与"广播"的分界：你一张嘴，它必须闭嘴。
自测里断言的是行为（状态收敛、不再有新句子、队列清空），不是断言某个实现细节。

### 16.6 怎么触发

| 通道 | 用法 |
|---|---|
| 控制面 | `speak`（带 `text`；`auto=True` 且 `speak_replies=false` 时直接跳过）、`shutup` |
| MCP 工具 | `voice_pill_speak(text)` / `voice_pill_shutup()` |
| Codex 回合结束 | `Stop` 钩子 `hook_stop.py`：读 stdin 的 `last_assistant_message`，调 `speak(auto=True)` |
| 默认 | **按需**。`speak_replies=false` 是默认值，所以 `Stop` 钩子默认什么也不做——只有你明确要听，它才出声 |

`Stop` 钩子是本轮唯一"每回合都会跑"的东西，所以它的契约是**任何异常都吞掉、
任何输入都吐 `{"continue": true}`**。它绝不能因为 TTS 出问题而拖慢或拦住一个回合。
这一条被 `tools/speak-selftest.py` 用 4 种载荷（有正文 / 空载荷 / 空正文 / 不是 JSON）
× 3 条断言（rc=0 / 合法 JSON 且 `continue` / 5 秒内）钉死；连控制面不可用（临时
`LOCALAPPDATA`）那种情况也在载荷里。

### 16.7 验证到哪一步

`tools/speak-selftest.py`，**42 项全过**：

* **模型**：目录解析得出来、六个必需文件齐全、且与 ASR 模型并排（不写死盘符）
* **文本清理 5 项**：代码块变成"（代码块略）"、链接只留标题、行内代码去反引号、
  列表/标题记号去掉、正文一个字不改
* **切句 2 项**：中英标点都认；超长句会被断开
* **连通性 6 项**：整段只开一条输出流、句间没有死气（<= 0.15 s）、开头不用等太久、
  总耗时接近音频本身（见 16.8）。假流**照真实代价打桩**（开流 0.34 s、写按实时阻塞），
  否则「逐句重开流」那种写法在假流上照样跑得飞快，等于没测
* **真合成 5 项**：调用方不被阻塞、音频真的出来（`_open_stream` 打桩成只记录，默认不发声）、
  时长合理、懒加载只发生一次
* **打断 4 项**：说话时状态为"在说"、`stop()` 后很快收敛、不再有新句子、队列已清空
* **静置释放 5 项**：到点释放、没到点不释放、配 0 = 一直留着、释放后还能再加载
* **`Stop` 钩子安全 12 项**：见 16.6

音色表另有尺子：`tools/tts-voice-map.py --probe`（数目自检 + 基频分界线）。

### 16.8 连贯性是量出来的：逐句重开流的代价（2026-10-03 补）

试听样本发出去之后，用户的原话是某条音色「连贯性表达效果差很多」。顺着这句话去量，
量出来的**不是音色的问题，是流水线的问题**——第一版的播法是「按句切、合成一句、
播一句」，而每个句号后面都白送两段死气：

| 来源 | 实测 | 为什么会落在停顿里 |
|---|---|---|
| `sd.OutputStream` 开一次关一次 | **0.34 s**（首次 0.95 s） | `_play()` 是 `with sd.OutputStream(...)`，每句重开一次 |
| 下一句的合成耗时 | **2.0 s**（那句 4.6 s 音频） | `stream.write()` **按实时走**（写 1 秒音频阻塞 1.03 秒），所以「合成 → 播 → 再合成」是串行的，合成时间整段落在停顿里 |

同一段文本（音频本身 6.40 s）：逐句重开流的墙钟是 7.40 s（不含中间的合成），
而只开一条流连写是 6.76 s。真实播放里还要加上那 2.0 s 合成，一段两句的回话中间
就能空出 **2 秒多**。

改法两条，都在 `_speak_one()` 里：

1. **整段只开一条输出流**，写满整段才关。设备开关费从「每句一次」变成「每段一次」。
2. **合成线程预取下一句**，让合成和播放重叠。预取位只有 1 个——够重叠，又不会在
   用户改主意之前就把一大段全合成出来（合成结果没法「取消」，只能不播）。

副产物是三个必须一起改的细节，少一个就出问题（都踩过）：

* **预取位满时生产者要能被 `stop()` 叫停**，否则它死等在一个已经没人取的队列上；
* **消费者不能只靠哨兵收工**——合成线程卡在一次长合成里时哨兵会迟到，所以消费者
  `get(timeout=0.2)` 自己回头看中断标志（这也是「按 Fn 立刻闭嘴」的一部分）；
* 被打断的合成线程可能还没退干净，而 `generate()` **不做并发保证**，所以合成
  加锁串行化，免得两句同时进模型。

尺子：`tools/speak-selftest.py` 的 `[连通性]` 一组。关键是假流**照真实代价打桩**
（开流睡 0.34 s、写按实时阻塞）——假流要是免费，第一版那种写法也能跑得飞快，
这条就等于没测。断言的是行为：整段只开一条流、句间空档 <= 0.15 s、总耗时接近音频本身。

这里要分清一件事，免得记错因果：**这一条不影响已经发出去的试听样本**。样本是整段
一次 `generate()` 出来的 wav，没经过播放流水线，所以样本里听到的停顿就是模型自己的
停顿（实测 3–4 段、合计 0.4–1.1 s，属正常）。也就是说，如果那条音色听着真的不连贯，
那是**音色本身**的问题；流水线这个毛病是这次顺手量出来的另一件事。客观数据上，
`zm_010` 是那批里最快的（5.4 字/秒，比中位数快两成），而它的基频起伏并不小
（半音标准差 0.54，是 13 个里最大的），所以「赶」比「平」更可能是听感差的原因——
要留住这个音色，就把 `tts_speed` 调到 0.9 左右。

### 16.9 边界（说清没做什么）

* **没有**做流式增量合成。`generate` 是一次一句，不是逐字吐。
* **预取只有 1 句**：够把合成和播放重叠起来，又不会在用户改主意之前就把一大段
  全合成出来——合成结果没法「取消」，只能不播，所以预取多了等于白花电和内存。
* **没有**做音色随会话/角色切换，也没有情感、语调控制——`sid` 就是一个整数配置。
* 合成时 sherpa-onnx 的 C++ 会往 fd 2 **直接**写一句 `Unknown token: ❓`
  （中文问号不在词典里，实测无害）。它绕开 Python 的 `sys.stderr`，所以只能在
  fd 层堵：`speak.py` 在合成那一小段窗口内把 fd 2 临时指向空设备，**且一定还原**。
  不堵的话每合成一句就往 `app.log` 塞一行噪音，几天就把有用的日志淹了。
* **常驻进程要重启**才吃到这套代码（改的是启动时加载的模块）。现在关掉 Codex
  再开就会自动重启它，见第 17 节。
## 17. 和 Codex 共同启停（2026-10-03）

要的形态是一句话：**开着 Codex，按 Fn 就有反应；关了 Codex，它自己收摊。**

### 17.1 为什么不是"启动时把 PID 传进去"就完了

三条实测事实把设计逼到了唯一解：

1. **拉起这条路必须能「后挂」。** 早先开机自启（见 11.2）挂的是看门狗不是真身，所以登录
   那一刻就已经有一个看门狗在跑、而那会儿 Codex 还没开。启动参数是一次性的，套不进这条路——
   看门狗得先活着、等 Codex 起来之后再**后挂**上锚点。
   （2026-10-04 起开机自启默认不装，看门狗通常由 `SessionStart` 钩子直接拉起：钩子先写纸条、
   再看要不要拉起，所以「先有看门狗、后挂锚点」这一步照旧。）
2. **钩子的直接父进程是 `cmd.exe`，不是 Codex。** 实测父链：

   ```
   python → cmd.exe → codex.exe（本次会话的运行时）→ ChatGPT.exe（桌面壳）
   ```

   所以必须沿父链往上走，不能只看 `os.getppid()`。
3. **取最外层那个。** `codex.exe` 只活在一次会话里，盯它会在会话切换时误关
   能力；`ChatGPT.exe` 才是「Codex 关没关」的判据。

于是分成两半：

* **拉起**：Codex 的 `SessionStart` 钩子（`plugins/voice-pill/hook_session_start.py`）。
  它做两件事——把锚点写成纸条，然后确保看门狗在跑。看门狗有互斥体，已经在守就
  什么都不做，所以每次开新会话跑一遍是幂等的（实测第二次 0.42 秒返回）。
* **收摊**：`src/anchor.py` + `src/supervise.py`。纸条落在
  `%LOCALAPPDATA%\VoicePill\anchor.json`，内容就 `{pid, image, at}`。看门狗每秒
  重读一次，变了就换人。

### 17.2 认人不认号：PID 会被复用

PID 会被系统回收再利用，几小时后「同一个号」很可能已经是别的进程。所以不存号，
存**句柄**：`OpenProcess` 拿到的句柄会钉住内核里的那个进程对象，编号再被复用也
影响不到它。判活不是轮询，是 `WaitForSingleObject` 挂上去（进程终止那一刻句柄
被置位），不吃 CPU。

开句柄时顺手核对一次**映像路径**，防止一上来就认错人：纸条写的是
`ChatGPT.exe`，而那个号现在是 `chrome.exe`，就拒收、不绑。

纸条靠不住的所有情况（读不到 / 格式坏了 / 是上一次 Codex 留下的 / PID 被复用）
一律当作「暂时没有锚点」**照常守着**——退回「常驻到天荒地老」的老行为。能力本身
比绑生命周期重要，绝不因为绑不上就不干活。

### 17.3 收摊走优雅路径，宽限期兜底（顺带踩到一个跳板的坑）

锚点一消失，看门狗不是强杀，而是走 `--stop` 那条**优雅路径**（置命名事件）：
真身要收尾（拔键盘钩子、关悬浮条、写配对的日志尾）。实测那对日志长这样：

```
[看门狗] Codex（pid=7436）退了，已请驻留实例收摊（最多等 180 秒）。
收到 --stop，退出。

=== 退出 2026-10-03 15:22:02 code=0 ===
[看门狗] Codex 退了，一起退。
```

宽限期 180 秒是照着「最长录音 120 秒 + 转写余量」定的。到点还没收完（多半正卡在
录音或转写里）才强制结束。

**强制结束必须连子孙一起杀**——`src/supervise.py` 的 `child_argv()` 起的是
`.venv\Scripts\pythonw.exe`，实测它是个**跳板**：自己会另外起一个真 `python.exe`、
然后等在那里。只 `terminate()` 跳板，引擎还在跑，而看门狗会以为收工了——正是
这个能力最该避免的「半死」。所以强杀走 `taskkill /F /T`。

### 17.4 冷启动那几秒：等，但别干等

用户在会话刚开起来就按 Fn，是最容易落空的一刻（引擎要起进程、装钩子、架控制面）。
钩子最多等 6 秒（实测这份机器冷启动落在 3 秒出头，3 秒会差一点点）。但**看门狗
一旦走了就立刻收手**：真出故障（模型目录被移走之类）时看门狗会连崩 3 次后放弃，
这时候再干等 6 秒就是白等，而且每开一次会话都要等。

这里踩过一个竞态：刚 `spawn` 出来的看门狗还没来得及拿互斥体，第一轮检查就判
「它不在了」→ 立刻放弃（日志里是 `ready_timeout`）。所以「不在了就收手」必须等
**先见过它活着**才算数。

不管哪种情况，钩子都要给 Codex 一行 `{"continue": true}`：钩子卡住会拖慢用户的
每一次开新会话。

### 17.5 验证到哪一步

`tools/supervise-selftest.py`，**47 项全过**：认人（只认 Codex 家族、取最外层）、
句柄（映像对不上就拒收、进程没了判活为假）、纸条（写得进读得出、坏了当没有、
内容没变不刷 mtime）、换人（变了跟着换、认不出就不绑、没了就松手）、收摊
（优雅优先、赖着不走的等过宽限期才强杀）、没绑锚点时一次收摊信号都不发。

一次**实机端到端**（不是打桩）：临时把纸条改成另一个可抛弃进程 → 看门狗换绑
（`[看门狗] 绑上 Codex：pid=7436`）→ 杀掉它 → 引擎 `=== 退出 … code=0 ===`
（成对的收尾行，说明是正常收的，不是被打死的）→ 看门狗跟着退。

自测也抓出过一个真 bug：锚点没了、走完优雅收摊之后，返回给上层的是「不是因锚点
而退」——行为对，信号错；调用方只看到「code 0，正常退出」，会漏掉「是被 Codex
带走的」这件事。

### 17.6 边界（说清没做什么）

* 关的判据是**进程**，不是窗口。桌面壳若把窗口收进托盘但进程还活着，不算关。
* 同一台机器上同时开着桌面 app 和 CLI 时，纸条会被**最后开的那次**覆盖；CLI
  退出会把引擎一起带走。本机只用桌面 app，没做优先级仲裁。
* `taskkill` 是外调命令，不是纯内核调用（纯内核要么上 Job Object，要么自己遍历
  进程树，都不划算）。
* 关 Codex 之后，**按 Fn 口述到别的程序**这件事也一并停了——这是「绑在一起」的
  应有之义，但值得知道：想恢复全局口述，重新打开 Codex 即可。

## 18. 口述落库（2026-10-03）

### 18.1 为什么是 Inbox，不是直接分类

知识库自己的约定是「先扔进来，别分类，每周清空一次」（`00_Inbox/_INBOX.md`），
而分类需要模型在场，常驻引擎不该背一个 LLM。所以这一步只做「判定 + 落盘」，
分类留给既有的 `/process-inbox`。

依据：`ANC.md` 第九节——先打穿一个具体业务点，不从流程和组织开始。

### 18.2 判定

两条路，命中任意一条就落库：

* **手指**：双击 Fn（0.35 秒内两下轻点）给「下一次口述」打上标记，HUD 提示
  「下次口述 → 落 Inbox」；那一次整句当正文，**不要求句子以口令开头**。标记只
  对下一次生效，一有正文就消费掉；再双击一下是取消。
* **口令**：转写文本以口令开头，默认 `记一下`（`capture_prefixes` 可配多个）。

为什么加手指这条路：口令要靠 ASR 把「记一下」听对，而本机这个模型的毛病恰好
是英文/技术词被听成中文同音字（issue #3）——口令自己也会被听歪，于是落库静默
不触发。手指不经过 ASR，这条触发路径与识别准确率**解耦**。

为什么不是「录音里按某个键」：Fn 按着的时候再按别的键，会被笔记本的 Fn 组合键
（音量 / 亮度）先吃掉；而轻点 Fn 今天什么都不做，是现成空着的手势。

判定是纯函数 `capture.decide(text, prefixes, armed)`，所以换触发方式只动热键层；
`capture.parse()` 仍是「只认口令」的那一半。

未命中时行为与从前完全一致。

### 18.3 落盘

`capture.write()` 用 `O_CREAT|O_EXCL` 创建 `00_Inbox/YYYY-MM-DD-HHMMSS.md`，
同秒撞名退到 `-2`、`-3`……最多退到 `-99`（`_MAX_SEQ = 100`），**绝不覆盖**；
写坏的文件删掉，不留残件。行尾 LF。

frontmatter 带 `type/inbox`——这是本次给知识库补的一个 type 值，见
知识库的 `_词表.md` 与 `_资产契约.md`。

### 18.4 失败与配置

写失败**不丢字**：报错后改走普通粘贴。默认关闭，`settings.json` 里配
`capture_dir` 才生效，仓库里不写任何机器路径。

标记亮着但落库没开（`capture_enabled` 关着、或 `capture_dir` 是空的）时，按普通粘贴处理，并往 stderr 打一行 `[落库标记]` —— 不静默。

三个配置项与其默认值（`src/config.py` 的 `Settings`）：

* `capture_enabled = False` —— 总开关；默认关。
* `capture_dir = ""` —— 落库目标目录；留空即不落库。
* `capture_prefixes = ["记一下"]` —— 触发口令，可配多个。

## 19. 控制面第二张口子：NDJSON（2026-10-03）

控制面（第 12 节）原来只有一条口子：`multiprocessing.connection` 的命名管道加 authkey。
插件侧要换成 Go 单 exe（第 20 节），而那条线只有 Python 能说。这一节记新增的第二条
口子——一行一条 JSON，任何语言的标准库都读得懂。旧口子一个字不改。

### 19.1 为什么不复刻 pickle

`multiprocessing.connection` 在 Windows 上确实就是命名管道，但它的**线格式是 Python 私有的**：

* 分帧是 `struct.pack("!i", n)` 写一个 4 字节长度头，后面跟 pickle 载荷（`Connection._send_bytes`）；
* 握手是 Python 自己那套 HMAC-MD5 挑战应答。

非 Python 端要接，只有两条路：复刻 pickle（含协议版本与类查找），或者复刻这套分帧加
握手。两条都不划算，也难保证跟 CPython 逐字节兼容——今天能跑，明天 CPython 改了协议就得
跟着改。

所以另开一条**语言无关**的口子：UTF-8、一行一条 JSON、HMAC-SHA256 挑战应答。这三样是
每个语言的标准库自带的东西，不用为它复刻任何私有格式。

### 19.2 协议

* **管道名**：`\\.\pipe\VoicePill-Json-` + `sha256(normcase(app_dir()))[:16]`（hex，小写），
  `app_dir()` 就是 `%LOCALAPPDATA%\VoicePill`。与旧口子**同源**：旧口子用的也是
  `sha256(normcase(app_dir()))[:16]` 这个 tag，只换前缀。`normcase` 复刻 Python 在 Windows
  上的行为（转小写、`/` 换成 `\`）。自测可用 `VOICEPILL_JSON_PIPE_NAME` 整名覆盖，不碰真身。
* **密钥**：`%LOCALAPPDATA%\VoicePill\bridge.key`，文件里 64 个 hex 字符 = 32 字节。先起的
  造（`O_CREATE|O_EXCL`），后起的读。两条口子共用这一份。
* **帧序**（一次连接一条请求，五步）：

  ```
  服务端 -> 客户端   {"nonce": "<32 位小写 hex>"}        # 16 字节随机数
  客户端 -> 服务端   {"auth": "<64 位小写 hex>"}          # HMAC-SHA256(key, ASCII(nonce))
  服务端 -> 客户端   （鉴权失败才回 {"ok": false, "error": "..."}，随后关闭）
  客户端 -> 服务端   {"cmd": "status", "args": {}}
  服务端 -> 客户端   {"ok": true, "data": {...}}  |  {"ok": false, "error": "人话"}
  ```

  注意第三步：**鉴权通过时没有中间 ack**，服务端直接等第四步的请求行；只有失败才多回那
  一行 `ok:false`。（这一条踩过一次：实现里若自作主张补一个 ack，两边就错位。）
* **分帧**：一行一条 JSON，紧凑（`separators=(",", ":")`、`ensure_ascii=False`）加 `\n`，
  UTF-8。单行上限 64 KiB（`MAX_REQUEST_BYTES`），超了报错，不无限读。
* **命令**：与旧口子逐字一致的七个——`status` / `start` / `stop` / `cancel` / `take` /
  `speak` / `shutup`。
* 建连超时沿用旧口子的 3 秒，空闲上限 60 秒。
* **金标准向量**（Go 侧 `internal/bridge` 单测钉死，Python 侧 `tools\bridge-json-selftest.py`
  同一条）：`HMAC-SHA256(key = bytes 0..31, msg = ASCII "0" 重复 32 次)`
  = `9f8f7fbc3e6c1c6192a185bc2305596bb4681df6bb51f544f37c373679a5fe6f`。

### 19.3 为什么保留旧通道

* **旧口子一个字不改**，回滚就只是删掉新东西，不用动老路径。
* 两条口子**共用同一份 handler**：`src\main.py` 里两个 server 都传 `self._bridge_command`，
  共用同一份 `bridge.key`。所以新口子不是「另起一个引擎」，只是同一个引擎多开了一张门。
* 尺子：`tools\bridge-selftest.py`（20 项，旧口子全程要绿）与
  `tools\bridge-json-selftest.py`（75 项，专盯新口子：金标准、坏输入、64 KiB 长度闸、
  60 秒空闲关连接）。

## 20. 插件侧换 Go 单 exe（2026-10-03）

### 20.1 一个二进制两种身份

`bin\voicepill.exe` 一个文件装两种身份，靠 argv 分：

* **不带子命令** → MCP stdio 服务端，注册八个工具：`voice_pill_status` /
  `voice_pill_listen` / `voice_pill_stop` / `voice_pill_cancel` / `voice_pill_take` /
  `voice_pill_speak` / `voice_pill_shutup` / `voice_pill_prompt_hook`。工具名与描述文字
  逐字照抄 Python 版 `plugins\voice-pill\mcp_server.py`。
* **带子命令** → 命令行钩子入口：`session-start` / `prompt-submit` / `stop`，分别对应
  Python 版的 `hook_session_start.py` / `hook_prompt_submit.py` / `hook_stop.py`。

两种身份共用同一套内部包：`internal/bridge`（控制面客户端）、`internal/engine`（引擎根
解析、看门狗、锚点）、`internal/tools`（八个工具）、`internal/hooks`（三个钩子）。

为什么要单 exe：这三个钩子**每次提交 / 每轮 / 每次会话**都会被拉起，MCP 服务端每个会话
拉起，都在用户能直接感觉到的关键路径上，起一个解释器太贵。单 exe 还省掉了那份只为装
`mcp` 而存在的插件 venv。

### 20.2 钩子为什么还包一层 .cmd

钩子命令写的是 `<PLUGIN_DIR>\hook-session-start.cmd`（另两个同理），`.cmd` 里只有两行：

```
@echo off
"%~dp0voicepill.exe" session-start
```

包这一层是为了拿到 `%~dp0`——**插件自己被装在哪儿**（经目录联接就是 Codex 看到的那个
路径）。它由 cmd 在运行时算出来，exe 里不用带任何机器路径；同一个 exe 换个机器、换个
用户名照样能跑。

没有让 `.cmd` 直接写 exe 全路径，也是同一个道理：全路径正是要渲染进 `hooks.json` 的
机器路径，多一处就多一处漏。`%~dp0` 把「机器路径」只留在渲染产物里，模板与仓库里什么都
没有。

### 20.3 不再需要的那个 UTF-8 补丁

Python 侧有一处 `src\console.py::make_output_safe()`：控制台或管道下 `sys.stdout` 会退回
locale 编码（简体中文机器上是 GBK），往 stdout 打中文或 `✅` 会**整段乱码甚至直接崩**。
所以 Python 版每个入口都得先包一层。

Go 侧不需要这个补丁：`os.Stdout` 就是字节流，源码是 UTF-8，写出去就是 UTF-8。钩子里那行
JSON 用 `json.Encoder` 直接写，天然成立——这是选单 exe 顺带省掉的一处机器相关补丁。

### 20.4 SessionStart 复刻了哪几件事

`hook-session-start.cmd` → `voicepill.exe session-start`，按顺序做四件事，全部对齐 Python 版
`hook_session_start.py`：

1. **写锚点纸条** `engine.WriteAnchor`：沿父链回溯**最多 16 层**，找**最外层**那个
   `codex.exe` / `chatgpt.exe`，把 `(pid, image)` 落到 `%LOCALAPPDATA%\VoicePill\anchor.json`。
   Toolhelp32 取父链的路线已与 Python `anchor.find_anchor()` 在同一进程树里**逐字对拍**
   （pid 与 image 一致）。
2. **解析引擎根**（三级）：环境变量 `VOICEPILL_ENGINE_ROOT` → exe 自解析自己的真实位置 →
   `%LOCALAPPDATA%\VoicePill\engine.json`。最后一级是「exe 被挪走 / 经联接解析不出」时的兜底。
3. **幂等拉起看门狗** `EnsureSupervisor`：靠互斥体 `Local\VoicePill.Windows.Supervisor` 守卫，
   已有则跳过（日志记 `supervisor_already_running`），不重复拉。
4. **等就绪** `WaitReady`：只有这一轮真的拉起了才等，每 0.3 秒探一次 `status`，最多 6 秒。

两条铁律：① 任何情况下 stdout **恰好一行** JSON（不打，Codex 会等，钩子卡住等于对话卡住）；
② **永远返回 0**——引擎没开、管道断了、正文超长，都不许拦住用户这一轮。全程异常只记日志，
吞掉。

另外两个钩子：`UserPromptSubmit` 把队列里的字作为本轮附加上下文注入（正文前缀与 Python 版
逐字节一致）；`Stop` 把助手正文 `strip()` 后按**字符**截 4000，交给引擎 `speak(auto=true)`，
整段预算 5 秒。

## 21. 安装与仓库洁净（2026-10-03）

### 21.1 模板 + 渲染 + gitignore

插件里有两处**只能是绝对路径**：`.mcp.json` 的 `command` / `cwd`，以及 `hooks/hooks.json`
里三个钩子命令。Codex 会把插件整包拷进自己的 cache，相对路径在那边解析不了。

做法是**模板 + 渲染**：仓库里只留

* `plugins\voice-pill\.mcp.json.template`
* `plugins\voice-pill\hooks\hooks.json.template`

占位符 `<PLUGIN_DIR>` 由 `plugins\install.py` 在安装时替换成目录联接路径，写到去掉
`.template` 的同名文件。那两个产物是**构建产物、不是项目文件**，由 `.gitignore` 挡住：

```
plugins/voice-pill/.mcp.json
plugins/voice-pill/hooks/hooks.json
plugins/voice-pill/voicepill.exe
```

写产物之前，`install.py` 先 `git check-ignore -q` 确认它真的被忽略，**没被忽略就拒绝落盘**
——免得哪天机器路径又被 `git add` 回仓库。

目录联接：`%USERPROFILE%\plugins\voice-pill` → 本仓库 `plugins/voice-pill`，仓库是唯一源码。
为什么绕这一道：本仓库路径带 `&`，Codex 侧的命令串会被 cmd 拆断（第 13 节）。

### 21.2 engine.json

`%LOCALAPPDATA%\VoicePill\engine.json`，内容一行 `{"root": "<仓库根>"}`。

它是**机器侧**状态文件，跟 `settings.json`、`bridge.key` 同处，不进仓库。用途是三级引擎根
解析的**第三级兜底**：exe 通常会自解析成功，engine.json 只在「exe 被挪走、或经联接解析不出」
时才读到。由 `install.py` 写。

### 21.3 删掉了什么

* **插件 venv 与 pip**：原来插件要一份只装了 `mcp` 的独立 venv
  （`%LOCALAPPDATA%\VoicePill\plugin-venv`），`install.py` 要建 venv、跑 pip。换成 exe 之后
  全删：安装只做「建目录联接、放置 exe、渲染模板、写 engine.json、`codex plugin add`」。
* 插件不再需要 `python.exe` 与那份 venv。引擎本体（仍 Python）继续用仓库自己的 `.venv`，
  两者互不相干。

exe 体积实测 **8 633 856 B（8.23 MiB）**（`-trimpath -s -w`），不是早先估的 12 MB。

## 23. 提前拉起：登录哨兵（2026-10-05）

§17 定的形态是「开 Codex 自动拉起」，拉起点是 `SessionStart` 钩子。2026-10-05 晚实测出一个洞：
**钩子打得比应用晚**。

### 23.1 实测时间线（同一台机器，plugin.log 与 app.log 对读）

| 时刻 | 事件 |
|---|---|
| 21:52:04 | `--stop` → 引擎退出 code=0 → **看门狗一起退**（设计如此） |
| 21:58:35 | Codex 桌面壳 `ChatGPT.exe`（pid=19168）起来 |
| **21:59:30** | `hook_session_start source=startup` → `supervisor_spawned` |
| 21:59:34 | `ready` |

也就是说，应用起来到钩子打出之间**有 55 秒**，这段时间里引擎和看门狗都不在，按 Fn 没有任何反应；
钩子打完还要再等约 4 秒预热（模型加载）。这段窗口里按 Fn 会录到一个 0 秒的空音——日志写的是
「麦克风没出声 —— 设备可能被别的程序占着」，**那是误导**，真因是刚起还没热。

### 23.2 为什么只改钩子不够

钩子的时机是 Codex 定的，插件改不了：桌面壳起来之后并不立刻开会话，`SessionStart` 要等一次会话
真的开始才打。所以「应用一露面就拉起来」只能由应用之外的东西做——这就是哨兵。

### 23.3 设计

`voicepill.exe sentinel`：一个登录时起的常驻小进程（**Go 单 exe，不带解释器**，判据见守则 1），
每 **2 秒**扫一次系统进程表，认出 Codex（`chatgpt.exe` / `codex.exe`，与锚点同一套判据）就：

1. 把锚点纸条写成**它**——哨兵不是 Codex 的子孙，父链里没有 Codex，所以只能先扫出候选、再用
   `engine.FindAnchorFrom` 各自往上认最外层那个；
2. 幂等拉起看门狗（`engine.EnsureSupervisor`）。

之后盯到它退出、回到等待，等下一次应用启动。纸条与看门狗都是钩子那套现成物，所以哨兵与钩子
**谁先到都不冲突**：纸条写的是同一个 pid，后到的看到没变就一个字节都不动；看门狗有互斥体，
重复拉只会得到 `supervisor_already_running`。

**纪律：不跟「明确停过」对着干。** 纸条挡在拉起之前——纸条上已经写着这个 pid 就不动。所以
`main.py --stop` 之后（纸条还在、Codex 还开着），哨兵不会偷偷把引擎再拉起来，与 §17 的
「退出码 0 就一起收摊」是同一条纪律。代价是「看门狗自己崩了而 Codex 还开着」这一种情形哨兵不管，
下次会话开始时钩子照旧兜底。

### 23.4 代价与目标

* 代价：登录后多一个常驻小进程。**实测**：工作集 9.9 MB；60 秒里累计 CPU 时间 0.031 秒（约单核
  0.05%，2 秒一次 `CreateToolhelp32Snapshot` 就是这点开销）。**引擎本体照旧不常驻**，
  没开 Codex 时不会白占内存。
* 目标：开 Codex 后 **10 秒（±5 秒）**内按 Fn 就有人应答。落点 = 扫描 ≤2 秒 + 预热约 4 秒
  （21:59:30→21:59:34 实测）≈ **6 秒**。

### 23.5 命令

```powershell
voicepill.exe sentinel --install      # 登记登录自启（HKCU\...\Run，用户级，不用管理员）
voicepill.exe sentinel --uninstall    # 撤掉那一行
voicepill.exe sentinel --status       # 登记没有 / 哨兵在不在跑 / 锚点是谁
voicepill.exe sentinel --once         # 只走一轮（排查用；不改常驻状态）
voicepill.exe sentinel --stop         # 请正在跑的哨兵退出（引擎不受影响，仍归看门狗管）
```

### 23.6 验证到哪一步

* `go test ./internal/sentinel/`：八个用例，全用假口（不扫真进程、不写真纸条、不拉真看门狗、
  不碰真注册表）。其中一条是测试逼出来的真 bug：进程表里还挂着「刚断气」的号，认下来会给一个
  已死进程写锚点，等于白拉一次——现在认下来之前先判活。
* `tools/pluginexe-selftest.py`：从 61 项加到 **80 项**，新增一段哨兵尺子（假进程表 + 真 exe +
  自己的注册表测试子键）：认下假 Codex、写锚点、拉不起引擎只剩 `supervise_missing`、第二趟记
  `note_kept` 不重复绑、没有 Codex 时说没找到、`--install/--status/--uninstall` 能写能读能删、
  常驻那一档会写下自己的纸条。测试子键跑完即删，真 Run 键一个字节不碰。
* **真机端到端（2026-10-05 22:36，实测）**：引擎与看门狗先停干净（`main.py --stop`，确认进程
  表里没有 `supervise.py` / `main.py`）、删掉锚点纸条、再把哨兵起起来。时间线：
  `sentinel_start` → **0.3 秒** `sentinel_bound` → `supervisor_spawned` → `看门狗启动` →
  `驻留启动` → 控制面就绪，全程 **3.0 秒**。加上哨兵最长 2 秒的扫描间隔，最坏约 **5 秒**，
  落进「10 秒（±5 秒）」。量法：`plugin.log` 的 `sentinel_bound` 到 `app.log` 的
  `驻留启动` 之差。
* **不跟 `--stop` 对着干（实测）**：`main.py --stop` 之后盯 20 秒，`plugin.log` 里没有一条
  哨兵动静——纸条还在、Codex 还开着，它就不动手。修好引擎的办法是下次钩子/工具调用
  （`engine.Ensure` 那条路）或者重启 Codex，不是让哨兵偷偷回滚用户的决定。
* 结构问题：哨兵认下一个 Codex 之后就只盯它到退出（`watchApp`），期间不再扫表。所以
  「看门狗自己崩了、Codex 还开着」这一种情形哨兵确实不管——要么下次钩子/工具调用补上，
  要么另设计一条「只补看门狗、不违 `--stop`」的判据（还没做）。

### 23.7 一处必须知道的手工步骤

插件目录里那份 `voicepill.exe`（`plugins/voice-pill/voicepill.exe`，钩子与 MCP 真正跑的那份）被
运行中的 MCP 进程锁着，**换不了**。所以改完 exe 之后要：关掉 Codex → 跑
`.venv\Scripts\python.exe plugins\install.py` → 再开 Codex。这一步不能省，否则跑的还是旧 exe
（实测：旧 exe 会回 `voicepill: 不认识的子命令 "sentinel"`）。

### 23.8 认根那一处补丁（2026-10-05）

**症状**：从开发那份 `bin\voicepill.exe` 起哨兵，认下 Codex 之后 `plugin.log` 写的是

    engine_root source=self root=<仓库的上一级>              ← 少了一级
    supervise_missing path=<仓库的上一级>\src\supervise.py

于是纸条写了、看门狗没起、引擎一直没起来——按 Fn 没反应。

**根因**：`engine.selfRoot` 把「exe 所在目录往上两级＝仓库根」写死了，这条只对
`<仓库根>\plugins\voice-pill\voicepill.exe`（插件那份，install.py 摆的）成立。开发那份摆在
`<仓库根>\bin\` 下，上两级正好落到仓库**外面**，而自解析「成功」返回了非空路径，第三级
`engine.json`（install.py 写下的、正确的根）根本没机会被读到。

**改法**：`rootFromExeDir` 不数级数，改成从 exe 目录往上认标记——`src\main.py` 与
`src\supervise.py` 都在才算仓库根，最多 4 级；认不出就回空串，交给 `engine.json`。
两种摆法（`plugins\voice-pill` 两级、`bin` 一级）都罩住，认错根（会拿别人的 supervise.py
起一个不是这个仓库的引擎）比认不出更糟。`resolveRoot` 顺带把「自解析回空串」与「自解析报错」
分成两条日志（`engine_root_self_missing` / `engine_root_self_failed`），免得日志里出现
`error=<nil>`。

**代价**：`rootFromExeDir` 每次解析根多两次 `os.Stat`（最多 4 级），只在起钩子/哨兵/拉引擎时
走一次。

**尺子**：`TestRootFromExeDir` 从「一条纯路径断言」改成真建目录树的四条用例（插件那份 / 开发那份 /
仓库根自己摆一份 / 摆在外面认不出），`TestResolveRootOrder` 补上「自解析回空串要退 engine.json」。
