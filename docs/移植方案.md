## 1. 复用什么 / 重写什么

| 层 | 判定 | 说明 |
|---|---|---|
| 转写算法与协议 | ✅ 复用 | Go/Rust 源码跨平台，交叉编译即可 |
| 进程契约 | ✅ 复用 | stdin 裸 PCM16LE 单声道 → stdout NDJSON。平台无关，**不要改** |
| 音频格式 | ✅ 契约不变 | 换的只是采集实现 |
| 热键 | ⚠️ 重写 | Fn 在 Windows 不可见，必须换绑 |
| 采音 | ⚠️ 重写 | AVAudioEngine → WASAPI |
| 粘贴 | ⚠️ 重写 | CGEvent ⌘V → SendInput Ctrl+V。**语义可照搬**（见第 5 节） |
| 悬浮窗 / 玻璃 | ⚠️ 重写 | Liquid Glass 无对应，降级为半透明条 |
| 打包签名 | ✅ 反而更简单 | Windows 无强制签名 |

> ### ⚠️ 工具链 ≠ 目标（`--target` 会失败，别用）
>
> `rustup toolchain install stable-x86_64-pc-windows-gnu` 装的是**工具链**，
> 不是给默认 msvc 工具链装 **target**。所以这样写会挂：
>
> ```bash
> cargo build --target x86_64-pc-windows-gnu ...      # ✗ error[E0463]: can't find crate for `core`
> ```
>
> 报错还很有迷惑性——它长这样，看着像 rlib 不兼容，其实只是 std 没装：
>
> ```
> error[E0463]: can't find crate for `core`
>   = note: the `x86_64-pc-windows-gnu` target may not be installed
> ```
>
> **正解：切到 gnu 工具链，不带 `--target`**（该工具链的 host 本身就是 gnu）：
>
> ```bash
> cargo +stable-x86_64-pc-windows-gnu build --release --locked \
>   --no-default-features --features streaming
> ```
>
> 另一条路是 `rustup target add x86_64-pc-windows-gnu` 给 msvc 工具链补 target
> ——能用，但等于两套工具链混着编，不如直接切干净。

> **`/usr/bin/link.exe` 是个陷阱。** 本机 `which link.exe` 会命中 MSYS2 的
> **coreutils `link`**（建硬链接的小工具），**不是 MSVC 链接器**。Rust 的
> `x86_64-pc-windows-msvc` 目标若按名字去捞链接器，捞到的就是它，
> 报错会莫名其妙。**因此 Rust 统一走 `x86_64-pc-windows-gnu`**：
> 链接器是 MSYS2 的 mingw `ld`，路径明确、不会撞名；
> 且同一套 mingw 工具链顺带把 Go 的 CGO + libopus 也喂饱了。
> 选 msvc 还得额外拉几个 GB 的 VS Build Tools，不划算。

| 装什么 | 为什么 | 覆盖 |

## 4. 三条路线

### 路线 C —— 最小可用（先跑通通路）

**做法**：Python 单文件。按住热键录音 → 松手写 WAV → 调**现成** `codex-asr` 0.1.2 做一次性文件转写 → 粘贴。

| 项 | 值 |
|---|---|
| 工作量 | 0.5 ~ 1 人日 |
| 依赖 | Python + `sounddevice` + `pynput` + `pyperclip`；codex-asr 0.1.2 上游二进制 |
| 有 | 按键录音、粘贴、目标窗口校验 |
| 无 | 实时字幕、HUD、断线 Retry、豆包后端 |
| 风险 | 极低。**不需要任何编译工具链** |

**用途**：1 天内验证「Codex 免登录转写在这台机器上到底通不通」。通路不通，后面全白搭。

### 路线 B —— 轻量壳（推荐主线）

**做法**：Python 外壳 + 编译出的 `codex-asr stream` / `freeasr` 子进程，完整复刻原版交互。

| 项 | 值 |
|---|---|
| 工作量 | 3 ~ 6 人日 |
| 有 | 实时字幕、悬浮条、双后端、断线留存 + Retry、目标窗口校验 |
| 无 | Liquid Glass（降级为半透明条）、辅助功能权限模型（Windows 不需要） |

## 5. Windows 侧要重新踩的坑

原版 `Sources/PasteController.swift` 里全是踩坑记录，以下语义必须照搬：

| 坑 | 原版做法 | Windows 做法 |
|---|---|---|
| **修饰键未释放导致粘贴失败** | 轮询 `CGEventSource.flagsState` 等到无修饰键按住再发 | `GetAsyncKeyState(VK_LCONTROL/VK_LSHIFT/...)` 轮询 |
| **目标窗口切换** | 记录录制开始时前台 app PID，粘贴前比对 | `GetForegroundWindow()` 比对 hwnd |
| **粘贴失败不要还原剪贴板** | 刻意跳过还原，让用户能手动粘 | 同 |
| **粘贴后延迟还原剪贴板** | 50 ms 写入延迟 + 400 ms 还原延迟 | 同（慢消费者需更久） |
| **剪贴板格式全量快照** | 保留富文本/图片 | `win32clipboard` 枚举格式；纯文本场景可降级 |
| **管道背压上限** | 256 KiB 封顶后终止子进程保留录音 | 同（`subprocess` stdin 写入计数） |
| **stdout 短读** | POSIX `read` 取当前可用字节 | `subprocess.stdout.read1()` 或非阻塞 `os.read` |
| **长按阈值** | 180 ms，轻点不触发 | 同 |
| **采音开流要异步** | AVAudioEngine 起来是即时的，原版没有这个问题 | **Windows 独有**，见 5.1 |

### 5.1 采音收尾竞态：`finish()` 跑在 `start()` 前面（2026-10-02 实测）

**这是 Windows/PortAudio 独有的坑，原版 macOS 没有**——`AVAudioEngine` 启动近乎即时，而 `sd.InputStream(...)` 的**构造函数本身是同步阻塞的**：实测冷启动 227 ms，`AudioCapture.start()` 整体 122 ms。这个数字比长按阈值（180 ms）还长，于是必然出事。

**故障形态**（`tools/fn-watch.py` 实测）：

```
FN up    vk=0xFF scan=0x63 ext=1 held=0.50s
ACT stop held=0.50s bytes=0 wav=44      ← WAV 只有 44 字节头，一个采样都没有
ACT start                                ← 收尾之后才打印，顺序反了
```

**根因**：`finish()` 那一刻 `start()` 还没执行到 `self._stream = sd.InputStream(...)`，所以 `_stop_stream()` 看到 `self._stream is None`，**什么都没停**；紧接着它把 WAV 关掉、置 `None`；然后 `start()` 继续往下跑，真的把流拉起来了 —— 结果是**一个永远在采集、但没人在写的泄漏流**，而且下一次录音还会撞上它。

**判据**：不能看「WAV 多大」，要看「`finish()` 之后计数还涨不涨」。已固化成 `tools/capture-probe.py` 的 [D] 回归段：

```
finish() 那一刻 0 字节；随后 1 秒又涨了 0 字节   ← 修好后必须是 0
流是否残留：否 ✅
```

**修法**（`src/audio.py`）：

1. `start()` 把开流丢进后台线程，**立即返回**（实测阻塞 122 ms → 2.5 ms）。
2. `_settle()` 先置 `_closing = True`，再 `_opened.wait(5.0)`，最后才停流。**顺序不能反**。
3. 开流线程在 `finally` 里检查 `_closing`：已置就地关掉刚建好的流，**绝不挂到 `self._stream`**。竞态窗口由此闭合。
4. `_opened.wait` 超时 5 秒也必须往下走 —— 宁可丢一段录音，不能让热键线程永久挂住。

**遗留**：开流 ~230 ms + 长按阈值 180 ms ≈ **Fn 按下后 410 ms 才开始记音**。按住说话时人通常在按下之后才开口，一般够用。彻底消除要改成「按下即预热、过阈值再开闸」，属 M5 打磨项。

### 5.2 退出信号：非主线程里的 `sys.exit()` 不生效（2026-10-02 实测）

原版靠 `NSApplication.terminate`，Windows 侧要自己管。`main.py` 里最初写的是在 `on_complete` 末尾调 `sys.exit(0)`，**不报错、也不退出**：

| 现象 | 实测值 |
|---|---|
| `--once` 跑完一次录音，应该退出 | 进程存活 **3 分钟以上** |
| 退出码 | 拿不到（进程还在） |
| 麦克风 | 一直被占着 |

**根因**：`on_complete` 不是从主线程进来的。调用链是 `live_session._read_loop`（读引擎 stdout 的线程）→ `threading.Thread(target=...)` → `on_complete`。而 `sys.exit()` 抛的 `SystemExit` **只终结抛出它的那个线程**，主线程的循环照转不误。（顺带：这也解释了为什么不能用 `KeyboardInterrupt` 之类去兜。）

**修法**（`src/main.py`）：改成事件驱动，`_shutdown()` 可从任意线程调用、幂等：

1. `self._stop = threading.Event()`；主循环退化成 `while not self._stop.wait(0.5)`。
2. `_shutdown()` 置 `_stopping` 防重入 → `_stop.set()` → `hotkeys.stop()`。
3. **`hud.quit()` 留在 `run()` 里**，不进 `_shutdown()` —— tkinter 只能在主线程收摊。

**验证**：`=== EXIT CODE 0 ===`，一次录音后进程自行退出，麦克风立即释放。

### 5.3 麦克风被占 → 静默空录音（2026-10-02 实测，是 5.2 的连带伤）

**故障形态**：假引擎如实回显 `收到 0 字节音频，约 0.00 秒`。看着像后端坏了，实际是**麦克风一帧都没出**。

**现场**：5.2 那个没退出的僵尸进程（PID 11352，19:30 启动）握了麦克风 15 分钟（19:30–19:45）。此后新起的实例**流能正常打开、不报任何错，但收不到一帧数据**——PortAudio 的共享模式流被饿死。链路每一段都是绿的，结果为空。

**为什么难查**：空音频被照常灌进引擎，引擎照常回一句关于 0 字节的话，用户看到的是**引擎的回显**，于是去查后端。真正的信号（麦克风没出声）在链路上游，而它不报错。

**修法**：

| 位置 | 改动 |
|---|---|
| `src/audio.py` | 新增 `_pcm_bytes` 计数（`_callback` 里与落盘同一把锁内累加），对外暴露 `bytes_captured` / `seconds_captured` |
| `src/main.py` | `on_stop()` 里 `capture.finish()` 之后**先体检再 `session.finish()`**：不足 `MIN_CAPTURE_SECONDS = 0.10` 秒就 `_abort_capture()` —— 撤掉会话（引擎都不启动）、删掉空 WAV、提示原因，**不送后端** |

**0.10 秒这个阈值怎么来的**：热键要求按住 ≥180 ms 才起录，开流又吃掉约 176 ms，所以最短的**有意图**的按住（约 0.3 秒）也能采到 ~0.12 秒，卡 0.10 不误伤；真正坏掉的情况实测就是 0.00 秒。提示文案按两种情形分开：

| 采到 | 文案 | 指向 |
|---|---|---|
| 0 秒 | 麦克风没出声（0 秒） | 设备被别的程序占着（含上一次没退干净的 Voice Pill），或刚被拔插 |
| 0 < t < 0.10 秒 | 录音太短（t 秒） | 按住主键的时间再长一点 |

**固化**：`tools/capture-probe.py` 的 [D]/[E] 段现在同时校验闸门输入（`seconds_captured=0.00 秒 → 跳过后端 ✅`）与计数器自洽（内部计数必须与 `on_pcm` 收到的字节数逐字节相等）。

**操作建议**：上一条僵尸就是「同时起了两个 `main.py`」的后果之一。调试期一律用 `timeout 150 python src/main.py --once` 包一层，别让"跑完不退出"留下占着麦克风的进程。

## 6. 键位设计（必须解决的硬问题）

**Windows 上 Fn 由键盘固件/EC 处理，绝大多数笔记本不上报给 OS**，`WH_KEYBOARD_LL` 收不到。方案：

| 候选键 | 优点 | 缺点 |
|---|---|---|
| **右 Ctrl** | 几乎无人用右 Ctrl，位置顺手 | 部分键盘无右 Ctrl |
| **右 Alt** | 同上 | 某些布局是 AltGr，会打字符 |
| **Caps Lock** | 位置极顺手 | 会牺牲大小写锁定；需改注册表关掉原功能 |
| **鼠标侧键** | 完全不占用键盘 | 需额外监听鼠标 |
| **长按 F1~F12 之一** | 通用 | 与其他软件冲突 |

**建议**：默认 **右 Ctrl**，并做成可配置项，首次启动引导选键。

> ⚠️ **以上是「实测前」的备选清单，已被 6.1 的实测结果取代。**
> 本机（ThinkPad T14p Gen 2）的 Fn **确实会上报给 OS**，所以主键直接用 Fn，
> 这份清单降级为「换机器/换键盘时的回退候选」。
> 落点在 `src/config.py: PRIMARY_KEY_CHOICES`（`fn` 为默认，其余四个仍保留）。

### 6.1 本机硬件（2026-10-02 实测）

| 项 | 值 |
|---|---|
| 机型 | Lenovo **ThinkPad T14p Gen 2**（`21KUA004CD`，`LENOVO_MT_21KU_BU_Think_FM_ThinkPad T14p Gen 2`） |
| 键盘设备 | `ACPI\LEN0071`（PS/2 标准键盘）+ `HID\INTC816&COL01`（HID 键盘） |

ThinkPad 的 Fn 由 **EC（嵌入式控制器）**处理。利好：BIOS 有 `Fn and Ctrl Key swap`、`F1–F12 as primary function` 等固件级选项，Lenovo Vantage 也能改 Fn 行为。风险：多数 ThinkPad 单独按 Fn **不向 OS 上报键码**。

**因此先跑探针实测，不预设结论。** 探针：`tools/fn-probe.py`（Raw Input + 低级钩子双通道）。

#### 探针实测结果（2026-10-02，两轮）

**结论：本机 Fn 会上报给 OS，且按下/松开成对 → 主键定为 Fn，可用「按住说话」。**

| 项 | 实测值 |
|---|---|
| 扫描码 | `0x63`，带 `E0` 扩展前缀 |
| vkCode | `0xFF`（无虚拟键映射——**必须认扫描码，不能认 vk**） |
| 可达通道 | HOOK 与 RAW **两条都抓得到** |
| 按下事件 | `WM_KEYDOWN` (`msg=0x0100`)，两轮共 23 次 |
| **松开事件** | **有**。`WM_KEYUP` (`msg=0x0101`)，两轮成对 |
| Fn + Esc | **零事件**。Fn Lock 在 EC 里完成，Windows 完全看不到（Esc 的 `0x01` 全程没出现） |
| 实测按压时长 | 0.11 / 0.44 / 0.45 / 0.45 / 0.46 / 0.53 / 0.58 / 0.73 / 2.15 s |

原始日志：`fn-probe.log`（第一轮，全键）、`fn-probe2.log`（第二轮，`--keyup --only 0x63`）。

两点提醒：

1. **第一轮探针自带判读误报。** 它只把 `scancode=0x00 vkCode=0x14`（Caps Lock 在 RAW 通道的怪癖）列为「非标准项」，反而漏掉真正重要的 `E0 63`。那个过滤条件写偏了 —— 看日志要**自己读去重表**，别信它的自动结论。
2. **第二轮结尾的「对照组 A/B 未抓到」也是误报**，因为该轮加了 `--only 0x63` 过滤，A/B 本就被滤掉。判读逻辑不认识 `--only` 这个开关。

> 探针为此加了两个开关：`--keyup`（记录松开事件）和 `--only 0x63`（只过滤指定扫描码）。默认行为不变。

**副作用：`pynput` 依赖被移除。** `vkCode=0xFF` 是无映射键，pynput 会不会原样透出未知；而裸 `WH_KEYBOARD_LL` 已被实测证明可用。`src/hotkey.py` 因此改为自己用 ctypes 挂钩子，顺带去掉一个依赖。

### 6.3 收不到键盘输入——已定论：不是进程的问题（2026-10-02）

**现象**：用 `tools/shell-selftest.py`（热键 + 采音，不依赖 ASR 引擎）验证热键链路，**从自动化工具拉起的 Python 进程，45 秒和 60 秒各跑一轮，原始按键事件都是 0 条**（连普通字母键都没有），而 `SetWindowsHookExW` 并没有报错——典型的「静默成功」。

早先还有一组更迷惑的数据：同一个 `fn-probe.py`，人手动跑抓到 23 次 Fn 按下，自动化跑是 0 条。

**当时的两个假设**：(1) 那段时间没人在按键；(2) 自动化拉起的进程不在交互桌面上，低级钩子绑桌面，跨桌面收不到。

**现在逐条证伪/证实：**

| 判定项 | 工具 | 实测结果 | 说明 |
|---|---|---|---|
| 窗口站 / 桌面 | `tools/desktop-probe.py` | `WinSta0` / `Default` | ✅ 就在交互桌面上 |
| 会话号 / 完整性 | 同上 | 会话 1，`0x2000 Medium` | ✅ 没有被沙箱降权 |
| 钩子 + 消息泵 | 同上（`SendInput` 自激自收） | 发 2 条收 2 条 | ✅ 链路本身是通的 |
| 会话里有没有物理输入 | `tools/input-liveness.py` | 60 秒内 `GetLastInputInfo` 跳了 187 次 | ✅ 输入在流动 |
| 钩子能不能看到物理输入 | 同上（同一次运行） | 第 176 次起钩子开始计数，最终 **21 条** | ✅ **能看到** |

**结论：假设 (2) 不成立。** 进程在交互桌面上、钩子链路完好、物理输入也能看到。那几次 0 条的唯一解释是**假设 (1)——窗口期内确实没人按键盘**。

注意 `input-liveness.py` 那一轮的形态很说明问题：**前 175 次输入事件钩子全是 0 条**——因为那是**鼠标**（`GetLastInputInfo` 键鼠都算，`WH_KEYBOARD_LL` 只算键盘）。直到人开始打字，第 176 次起钩子才开始计数。所以「会话有输入」和「键盘被按了」是两件事，不能混。

**为什么早先误判成"后台不行"**：跑完 60 秒、心跳显示进程活满全程、输出 0 条，就把 0 条归因给了进程。实际上没人按键和进程看不见输入，输出长得一模一样。**这是判据缺失，不是环境限制。**

**修正后的规矩：**

1. 涉及 `WH_KEYBOARD_LL` 的验证**可以**由自动化跑，不必非得人手动。
2. 但**任何时候都不许把「0 条」当成结论**——必须先证明窗口期内真有按键。`tools/input-liveness.py` 就是干这个的（鼠标动一下即可，不用按键）。
3. 测 Fn 这种「要人等」的项，别用固定窗口。用 `tools/fn-watch.py`：只打命中主键的行，默认听 900 秒，随时按都算数。理由是实测中 60 秒窗口里人往往在往输入框打字，134 行字母键把真正要看的 Fn 淹没了。

**本次顺手踩到的两个 ctypes 坑（都写在 `desktop-probe.py` 注释里）：**

| 坑 | 症状 | 真因 |
|---|---|---|
| `INPUT` 结构体只留了 24 字节联合体 | `SendInput` 返回 0，`err=87 ERROR_INVALID_PARAMETER` | x64 上 `MOUSEINPUT` 是 32 字节，系统眼里 `sizeof(INPUT)` = 40，`cbSize` 不等就一条都不发 |
| `GetCurrentProcess()` 没声明 `restype` | `OpenProcessToken` 报 `err=6 ERROR_INVALID_HANDLE` | 伪句柄是 64 位 `0xFFFFFFFFFFFFFFFF`，默认按 `c_int` 收成 `0xFFFFFFFF`，不再是合法伪句柄 |

两个都是**函数成功返回但结果无效**的类型，不看错误码根本发现不了。

### 6.4 凭据通路实测：三个后端全断（2026-10-02）

第 9 节把「Codex 免登录通路不通」列为**高风险**，实测下来风险应验，而且是**三路都不通**。

用 SAPI 合成一段真语音（`tools/make-test-audio.ps1`，发音人 Microsoft Huihui Desktop zh-CN，8.93 秒），转成裸 PCM（`tools/wav-to-pcm.py`）分别灌给两个引擎，**绕开麦克风和热键**单独验引擎通路。

| 后端 | 实测命令 | 结果 |
|---|---|---|
| Codex | `codex-asr.exe stream --sample-rate 24000 --input tmp/test-24k.pcm` | ❌ `Codex auth at ~\.codex\auth.json does not contain a ChatGPT access token` |
| 豆包 | `cat tmp/test-16k.pcm \| freeasr.exe live --quiet` | ❌ `rpc error: code = 2 desc = service discovery failure` |
| 本地中转 | `curl 127.0.0.1:15721/v1/models` | ❌ `HTTP 000`，端口没监听 |

**Codex 的真因**：`~\.codex\auth.json` **只有 39 字节**，内容是一个 13 字符的 `OPENAI_API_KEY` 占位符，**没有 `tokens`**（OAuth 令牌）。而且 `~\.codex\config.toml` 指向 `base_url = "http://127.0.0.1:15721/v1"` 的**本地中转**（`requires_openai_auth = true`、模型 `deepseek-flash`），说明这台机器的 Codex CLI 压根没走官方 ChatGPT 后端。

> ⚠️ 教训：自检里「文件存在 = ✅」是**假阳性**。`main.py --check` 原来就只看 `auth.json` 在不在，报 ✅ 而引擎照样失败。已改成**读内容**判 `tokens.access_token`，现在会明确报「只有 OPENAI_API_KEY（13 字符），无 ChatGPT OAuth 令牌」。
> **解**：跑 `codex login` 用有转写权限的 ChatGPT 账号重新登录。

**豆包的真因**：不是网络、不是代理（系统代理 `ProxyEnable=0`，已关；环境变量也无）。verbose 日志显示链路是**通的**：

```
loaded credentials from file  device_id=3119778226010346
connecting to ASR  url=wss://frontier-audio-ime-ws.doubao.com/ocean/api/v1/ws
ASR session ready  request_id=36766590-f91d-4f10-876d-c615eed47de0
→ Error: ASR: read backend response: rpc error: code = 2 desc = service discovery failure
```

WebSocket 握手成功、会话就绪，**服务端**才回错。文件转写（`transcribe`）与实时（`live`）两条路报同一个错，重试一致。且 —— 关键佐证 —— `service discovery failure` 这个串**不在客户端源码里**（`grep` 过整个 `vendor/FreeASR`），是服务端原样透传的。

客户端伪造的是豆包输入法安卓端（`internal/protocol/constants.go`：`aid=401734`、`version_name=1.1.2`、Pixel 7 Pro 的 UA）。字节跳动侧不再给这条逆向协议路由 —— **本机无解**，只能等上游适配。

> ⚠️ 附带发现：`freeasr doctor`（本该只读的体检命令）**会自动注册设备并申请令牌**，凭据写到 `~\.config\freeasr\credentials.json`。属该工具自身设计，但首次跑会静默产生一次对外注册。

**当时可用的替代**：`tools/mock-asr.py` —— 实现 NDJSON 契约但不真转写，把「收到多少字节音频」当转写文本回吐。用它可把链路里**除转写之外**的每一段（钩子、采音、重采样、管道背压、解码、粘贴）先钉死；粘出来的字节数与录音时长对不上就说明管道丢包。挂法：

```bash
# ⚠️ 路径里的 & 必须用引号包住：
#    bash 下裸着的 & 是「后台运行」运算符，命令会在此断句；
#    cmd  下裸着的 & 是命令分隔符，`set` 会在此截断，赋进去的值只剩前半截。
VOICEPILL_ENGINE="D:\Own_tools&skills\voice-pill-windows\tools\mock-asr.py" .venv/Scripts/python.exe src/main.py
```

cmd 里同理，引号要包住**整个赋值**：

```bat
set "VOICEPILL_ENGINE=D:\Own_tools&skills\voice-pill-windows\tools\mock-asr.py"
.venv\Scripts\python.exe src\main.py
```

### 6.5 后端选型定案：本地离线 SenseVoice（2026-10-03）

6.4 的三个后端全都不能用。6.2 定的「主键 = Fn」不受影响，受影响的是「谁来转写」。
2026-10-03 把能怪的对象逐个排掉之后，定案走**本地离线**。

**复验过程**

| 假设 | 怎么验的 | 结论 |
|---|---|---|
| 境外 IP 被拒 | 关掉 Clash 让出口回到国内（`doubao.com` 解析回 `49.7.200.4`）重跑 | ❌ 同一个错，假设不成立 |
| 音频内容/格式问题 | 灌 0.5 秒纯静音，0.47 秒返回同一个错 | ❌ 会话级失败，与音频无关 |
| 本工程移植引入 | 原版 macOS 仓库的 `vendor/FreeASR/internal/protocol/constants.go` 与本工程**逐字节相同**，上游 `HEAD` 仍是 `252f6387` | ❌ 上游级故障，原版 app 同样中招 |
| 本地网络链路 | 强制走本地代理 7897 与直连对比 | ❌ 两条路径同一个结果 |

握手**是**成功的（`TaskStarted` / `SessionStarted` 都能收到），错在服务端自己的
服务网格。这条非官方协议线在字节跳动侧恢复之前，本机无解。

**定案：本地离线（`local` 后端）**

* 引擎：`tools/local-asr.py`。Python 脚本，**不在 `bin/`** —— 它跟着工程走，
  `config.engine_path()` 对带扩展名的按工程根目录解析。
* 模型：sherpa-onnx + SenseVoice-Small **int8**，228 MB。本机放在
  `D:\VoicePill-models\sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`，
  写进 `settings.json` 的 `local_model_dir`。
* 下载源走 **ModelScope**（`WEAAEW/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`）。
  代理关掉后 GitHub Releases 与 hf-mirror 都超时，PyPI 与 ModelScope 正常 ——
  所以模型别从 GitHub 拿。

**实测（2026-10-03，本机 Ultra 5 125H / 31.5 GB，纯 CPU）**

| 项 | 值 |
|---|---|
| 识别速度 | RTF **0.027**（8.93 秒音频 0.245 秒出结果） |
| 准确度 | SAPI 合成句一字不差：`这是一段测试语音，用来验证语音转写引擎是否工作正常。今天天气不错。` |
| 模型加载 | 1.14 秒。读线程先起，加载与用户开口的时间重叠，不占额外延迟 |
| 中间结果 | 截前 3 秒能出「这是一段测试语音，用来验证。」；管道自测全程 8 条递增快照 |
| 全链路自测 | `pipe-selftest.py` ✅ 8.93 秒音频 9.41 秒跑完，exit 0 |

**中间结果为什么还保得住**：SenseVoice 不是流式模型，但快到可以对「已收到的音频」
整段重跑 —— 重跑间隔按上一次解码耗时的 4 倍退避，长录音不会越跑越落后（固定
1 秒间隔必然追不上：60 秒音频单次解码约 1.6 秒）。M3 的实时字幕因此没有降级。

**代价**：模型体积与首次下载；换机或换模型要重新指定 `local_model_dir`。
**收益**：不联网、不要账号、没有额度与封禁风险，也不受任何服务端改动影响。

> `codex` 与 `doubao` 两个后端**保留在代码里**，没有删。凭据已生成、provider
> 已写好，哪天 ChatGPT 订阅到位或豆包协议恢复，改 `settings.json` 一行就能切回。
