# 插件换 Go 单 exe 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** 插件侧交付物换成一个 Go exe（8 个 MCP 工具 + 3 个钩子入口），控制面新增一条语言无关的 NDJSON 通道，仓库工作区里不再出现本机绝对路径。

**架构：** 引擎（Python）里多起一条 NDJSON 命名管道，与旧的 `multiprocessing` 通道共用同一份 `bridge.key`、同一个命令处理回调。Go exe 是这条新通道的客户端：不带子命令时按 MCP stdio 服务端跑，带子命令时跑三个钩子。安装脚本只负责渲染两条绝对路径、放置 exe、写 `engine.json`。

**技术栈：** Go 1.27.0 + `github.com/modelcontextprotocol/go-sdk` v1.8.0（MCP 服务端）；Python 侧只用标准库（`ctypes` 走 Win32 命名管道，`hmac`/`hashlib` 做挑战应答）。

**规格：** `docs/superpowers/specs/2026-10-03-插件换Go单exe.md`

## 注意事项（环境踩过的坑，照做）

- 所有工程文件是 **LF、UTF-8 无 BOM**。写文件用 `io.open(p, "w", encoding="utf-8", newline="")`，或 `[System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding($false)))`。
- **Go 源码也必须 UTF-8**：工具描述、钩子提示语里都是中文。实测用 ASCII 写出来的 `状态` 在 `tools/list` 里就是 `??`，静默生效。
- 控制台是 GBK：命令输出先 `> "$env:TEMP\x.txt" 2>&1`，再 `Get-Content -Encoding UTF8`，否则中文是乱码。
- 自测一律用工程 venv：`<仓库根>\.venv\Scripts\python.exe`。
- **MCP stdio 的一个坑（实测两次）**：把整段请求喂给 exe 后**立刻关掉 stdin**，回复会丢——exe 退出码 0、stdout 是空的。写完请求要留 300 毫秒再 EOF，或者干脆用 SDK 自己的客户端（`mcp.NewClient` + `&mcp.CommandTransport{Command: exec.Command(exe)}`）。`tools\pluginexe-selftest.py` 必须照这个来。
- **GOPROXY**：默认 `proxy.golang.org` 拉得到 SDK 本体，但它的间接依赖（`golang.org/x/sync`、`golang.org/x/sys`、`segmentio/encoding`、`jsonschema-go`、`uritemplate`、`jwt/v5`）在本机实测会走 IPv6 卡死（`dial tcp [2607:...]:443: connectex ...`）。构建脚本固定 `$env:GOPROXY='https://goproxy.cn,direct'`（实测一次过）。
- 无参工具的入参类型用 `struct{}`：实测 `tools/list` 出的 `inputSchema` 是 `{"type":"object","additionalProperties":false}`。
- 工具返回值统一「一个 TextContent（紧凑 JSON）+ 同名结构化对象」：实测 `tools/call` 回的正是 `{"content":[{"type":"text","text":"{...}"}],"structuredContent":{...}}`，与 Python 版的文本输出逐字可比。
- 路径里的 `&` 红线、`%USERPROFILE%\plugins\voice-pill` 目录联接的由来（插件被整包拷进 Codex cache，相对路径解析不了）见移植方案第 13 节，本次不重新论证。
- 危险操作（删旧插件文件、改 `%LOCALAPPDATA%` 下的东西）按守则先问，授权后再动。

```python
# 语言无关的第二条通道（NDJSON）。跟旧通道同一个用户 tag，只换前缀。
JSON_PIPE_PREFIX = r"\\.\pipe\VoicePill-Json-"
JSON_PIPE_NAME_ENV = "VOICEPILL_JSON_PIPE_NAME"


def json_pipe_name() -> str:
    """NDJSON 通道的管道名。与 pipe_name() 同源，只有前缀不同。"""
    override = os.environ.get(JSON_PIPE_NAME_ENV, "").strip()
    if override:
        return override
    tag = hashlib.sha256(
        os.path.normcase(config.app_dir()).encode("utf-8")).hexdigest()[:16]
    return JSON_PIPE_PREFIX + tag


def auth_token(key: bytes, nonce: str) -> str:
    """挑战应答的应答：HMAC-SHA256(key, ASCII(nonce))，64 位小写 hex。"""
    import hmac as _hmac
    return _hmac.new(key, nonce.encode("ascii"), "sha256").hexdigest()
```

- [ ] **步骤 3：实现 `JsonBridgeServer`**

照 `BridgeServer` 的对外形状（`start()` / `stop()` / `alive` / `started` / `error` / `last_error`），内部改走 Win32：

- `WinDLL("kernel32", use_last_error=True)` 调 `CreateNamedPipeW` / `ConnectNamedPipe` / `ReadFile` / `WriteFile` / `DisconnectNamedPipe` / `CloseHandle`。
- `CreateNamedPipeW` 参数：`PIPE_ACCESS_DUPLEX`；`PIPE_TYPE_BYTE | PIPE_READMODE_BYTE | PIPE_WAIT`；`PIPE_UNLIMITED_INSTANCES`；出入缓冲各 `MAX_REQUEST_BYTES`（64 KiB）；安全属性传 `NULL`（与现有 `multiprocessing.Listener` 一样，靠默认 DACL 只对本用户开放）。
- 一个 accept 线程反复 `ConnectNamedPipe`；拿到连接就交给一条 `daemon` 线程，处理完 `DisconnectNamedPipe` 再回 accept。**任何一条坏连接都不许把 accept 线程带走**（旧通道的 `AuthenticationError` 教训，见移植方案 12.5）。
- 处理线程：写 `{"nonce": ...}`（`secrets.token_hex(16)`）→ 读一行 auth → `hmac.compare_digest` 比对 → 读一行请求 → `self._parse(request)`（复用旧的解析与 `COMMANDS`）→ 调 `self._handler(cmd, args)` → 写一行响应。
- 分帧：读到 `\n` 为止，行内 UTF-8；超过 64 KiB 直接回 `{"ok": false, "error": "请求超长"}` 并关连接。
- 空闲 60 秒：起 `threading.Timer`，到点 `CloseHandle` 这条管道——Windows 上这会打断阻塞中的 `ReadFile`，线程随即退出。句柄**只能关一次**：用一个 `threading.Event`（或锁）守卫，双关会把别的连接带崩。
- `stop()`：置事件 + 自己连一次自己来唤醒 accept（照抄 `BridgeServer.stop()`），只关自己这一条。

```python
def json_call(cmd: str, timeout: float = CONNECT_TIMEOUT_SECONDS, **args):
```

行为要求：

- 连不上 / 超时 → `BridgeError`，**不许挂住**（照旧通道 `CONNECT_TIMEOUT_SECONDS = 3.0` 的教训：握手没有超时参数，只能自己卡）。

- 单条请求上限 64 KiB（超了直接在本侧报错，不写进管道）。
- 超时实现：把读写放到工作线程，主线程等 `threading.Event`，到点关掉管道句柄（Windows 上会打断阻塞的 `ReadFile`）。

```go
	pipePrefix   = `\\.\pipe\VoicePill-Json-`
	pipeNameEnv  = "VOICEPILL_JSON_PIPE_NAME"

func appDir() (string, error) {
	base := os.Getenv("LOCALAPPDATA")
	if base == "" {
		return "", fmt.Errorf("LOCALAPPDATA 是空的，找不到 %s", keyFileName)
	}
	return filepath.Join(base, "VoicePill"), nil

// sha256(normcase(appDir())) 的前 16 个 hex 字符，前缀换成 -Json-。
func jsonPipeName() (string, error) {

		return "", err
```

## 偏差登记

计划写在动手之前，实做难免撞上它没料到的东西。这里只记「计划说 A、实做是 B」的条目，
按任务号排；理由后面括号里写证据落在哪，方便回头对质。**只记事实，不写本机路径。**

- 任务 2：计划第 210 行「处理完 `DisconnectNamedPipe` 再回 accept」→ 每条连接**新建一个管道实例**、用完 `CloseHandle`，accept 线程接着建下一条。理由：复用实例要处理「上一轮没排空」的残留状态，新建实例天然干净。（证据：`tools\bridge-json-selftest.py` 并发段，8 条连接各自拿到自己的回包。）
- 任务 2：计划第 213 行「空闲到点 `CloseHandle` 这条管道——Windows 上这会打断阻塞中的 `ReadFile`」→ **这条是错的**：`CloseHandle` 不取消挂起的同步 I/O。改成 `PeekNamedPipe` 轮询 + 绝对截止时间。理由：照抄计划的话，空闲回收根本不是「到点」回收。（证据：自测「连上不说话」段，闲着的连接在 60 秒那一档被服务端关掉。）
